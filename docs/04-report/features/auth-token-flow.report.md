### 1.3 가치 전달 (4관점)

| 관점 | 내용 |
|------|------|
| **문제** | 프론트가 로그인 응답의 accessToken을 버려서 로그인이 필요한 API를 하나도 호출할 수 없었고, 백엔드는 미인증 요청에 401이 아닌 403을 반환해 "재로그인 필요"와 "권한 없음"을 구분할 수 없었다. |
| **해결** | 백엔드는 미인증 401, 권한 부족 403, 재발급 실패 401을 JSON으로 반환하고, 프론트는 토큰을 메모리에 두고 모든 요청에 Bearer 헤더를 붙이며, 401이면 한 번 재발급 후 재시도하고 실패하면 로그아웃한다. "로그인 상태 유지" 체크박스도 구현됐다. |
| **기능/UX 효과** | 로그인 후 피드·댓글·북마크 등 보호 API를 쓸 수 있게 되고, 새로고침·새 탭에서도 로그인 상태가 유지되며, 세션 만료 시 화면이 자연스럽게 로그아웃 상태로 바뀌고, "로그인 상태 유지" 해제 시 브라우저 종료 시 자동 로그아웃된다. |
| **핵심 가치** | 이후 모든 로그인 기능(피드, 댓글, 좋아요, 북마크, 마이페이지)의 전제 조건을 해결했다. 토큰 보관·재발급 동시성 처리·세대 번호 경쟁 조건은 포트폴리오 포인트다. |

## 7. 회고 (Keep / Problem / Try)

### 7.1 잘한 점 (Keep)

- **역할 분리와 병렬 진행**: 백엔드(frontend-support-backend)와 프론트(frontend-lead)가 파일이 겹치지 않아 설계 §4의 API 계약만 공유하고 병렬 구현했다. 리뷰(frontend-code-reviewer)와 gap 분석(bkit gap-detector)도 병렬로 돌려, 코드 품질 관점과 설계 일치 관점의 결과를 함께 얻었다.
- **리뷰 → 수정 → 재리뷰 루프**: 1차 리뷰의 Must Fix 1건과 Should Improve 4건을 Act-1에서 고치고, 같은 리뷰어가 재리뷰해 해결 여부를 R 번호별로 확인했다.
- **토큰·세대 번호 설계**: single-flight + authGeneration으로 동시 401·StrictMode를 한 번에 처리하고, 로그아웃 중 재발급을 감지해 경쟁 조건을 원천 차단했다.
- **예외 분류 명시**: 401과 500의 경계를 명확히 하고(검증 vs 발급), 로그 레벨(debug vs error)을 나눠 운영성을 확보했다.
- **모듈 경계 유지**: client.js는 AuthContext를 import하지 않고 콜백(sessionExpiredHandler)만 등록해 순환 의존을 회피했다.

### 7.2 문제점 (Problem)

- **워크플로 미준수로 시작**: 계획 수립 전에 메인 세션이 에이전트·PDCA 절차 없이 백엔드·프론트 파일을 직접 수정하기 시작했다. 사용자가 이를 지적해 수정분을 `git stash`로 보관하고 Plan부터 다시 진행했다.
- **범위 결정의 부작용을 늦게 발견**: 계획에서 "로그인 상태 유지"를 범위 밖으로 뺐지만, 같은 계획의 "앱 시작 시 자동 복원"과 결합하면 체크 해제가 무의미해진다는 점을 Check 단계 리뷰에서야 발견했다(R-1).
- **병렬 검증의 정보 단절**: 리뷰와 gap 분석을 병렬로 돌리자 gap 분석이 리뷰 결과를 몰라 SC-4를 "미수행"으로 판정했고, 메인 세션이 문서를 통합하며 보정해야 했다.
- **작업 중단**: 사용량 한도로 Act-1 에이전트 두 개가 도중에 멈춰 재개가 필요했고, 보고서 에이전트는 턴 제한에 반복해 걸려 설계 문서에 코드와 다른 서술이 일시적으로 들어갔다(메인 세션이 대조해 정정).
- **테스트 환경**: test 프로필이 임의 포트로 떠서 Vite 프록시(8080)와 맞지 않아 재기동이 필요했다.
- **L2 기록 누락**: 브라우저 확인 결과를 항목별로 받지 않아 개별 시나리오 통과 여부가 남지 않았다.

- **범위 제외 항목의 교차 점검**: Plan에서 제외한 항목이 포함 항목과 결합했을 때 사용자에게 보이는 동작이 어떻게 바뀌는지 Plan 체크포인트에서 확인한다.
