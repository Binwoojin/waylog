# users 이메일·닉네임 유니크 제약 (동시 가입 정합성)

> **상태**: 코드와 테스트, 마이그레이션 SQL은 준비됐다. **운영 DB에는 적용하지 않았다.** 적용은 아래 3장의 선행 확인 뒤에 한다.
> **우선순위**: P1. 서버 중복 검사(`3ae69f1`)만으로는 동시 가입을 막을 수 없으므로 DB 제약이 마지막 방어선이다.

---

## 1. 문제

- 서버 중복 검사는 `existsByEmail`, `existsByNickname`으로 저장 전에 확인한다.
- 두 가입 요청이 같은 닉네임으로 동시에 들어오면, 둘 다 검사를 통과한 뒤 둘 다 저장될 수 있다.
- 이메일은 인증 티켓이 한 번만 쓰이므로 같은 이메일의 동시 가입은 거의 막히지만, 제약이 없으면 정합성을 보장할 수 없다.

## 2. 현재 구현

| 항목 | 내용 | 위치 |
|---|---|---|
| 엔티티 제약 | `uk_users_email (EMAIL)`, `uk_users_nickname (NICKNAME)` | `UserEntity` `@Table(uniqueConstraints)` |
| 마이그레이션 | `ALTER TABLE users ADD CONSTRAINT ...` (작성만, 미적용) | `backend/db/migrations/2026-10-07-users-unique-keys.sql` |
| 충돌 처리 | `saveAndFlush`에서 `DataIntegrityViolationException`을 받아 제약 이름으로 메시지를 고른다 | `AuthService.signup`, `duplicateAccountError` |
| 응답 | 400 `이미 사용 중인 이메일입니다.` / `이미 사용 중인 닉네임입니다.` / 그 외 일반 문구 | `GlobalExceptionHandler`의 IllegalArgumentException 처리 |
| 테스트 | 제약이 실제로 걸리는지, 5개 요청이 동시에 같은 닉네임으로 가입해도 한 개만 저장되는지 | `NicknameUniquenessHttpFlowTest` |

- 테스트 DB는 엔티티 기준으로 만들어지므로 `@Table`의 제약이 그대로 생긴다. 운영 DB는 `ddl-auto: none`이라 엔티티 제약은 적용되지 않고 마이그레이션 SQL로만 생긴다.
- 제약 이름은 엔티티와 마이그레이션 SQL이 같아야 충돌 메시지를 올바르게 고를 수 있다.

## 3. 운영 적용 전 필수 확인 (읽기 전용)

`backend/db/checks/readonly-precheck.sql`을 운영 DB에서 실행하고 결과를 확인한다.

1. **8장 중복 조회가 0행인지.** 행이 있으면 중복 계정을 먼저 정리한다. 정리 방법은 계정 데이터의 소유자와 상태를 보고 정한다. 이 과정에서 운영 데이터를 직접 바꾸지 않고 결정을 먼저 남긴다.
2. **8-1 기존 유니크 인덱스.** 이미 같은 컬럼의 유니크 인덱스가 있으면 해당 ALTER 문장을 건너뛴다.
3. **9장 콜레이션.** 아래 4장의 정책과 맞는지 확인한다.
4. **백업.** 운영 DB 백업을 받은 뒤 마이그레이션을 실행한다.

## 4. 이메일·닉네임 비교 정책

### 4.1 현재 동작

- 서버 검사와 유니크 제약은 모두 **DB 콜레이션**으로 비교한다. Java 쪽에서 대소문자나 공백을 따로 정리하지 않는다.
- 따라서 실제 의미는 컬럼 콜레이션이 정한다.
  - MySQL 8의 기본 콜레이션(`utf8mb4_0900_ai_ci`)은 **대소문자와 악센트를 구분하지 않는다.** `User@x.com`과 `user@x.com`은 같은 값으로 취급된다.
  - 같은 콜레이션은 끝 공백을 무시하지 않는다(NO PAD). `nick`과 `nick `은 다른 값으로 취급된다.
- 가입 요청의 이메일과 닉네임은 `trim`하지 않고 저장한다. 앞뒤 공백이 있는 값은 별개의 계정이 될 수 있다.

### 4.2 판단이 필요한 문제 (결정 전까지 현 동작 유지)

| 질문 | 현재 | 권장 | 영향 |
|---|---|---|---|
| 이메일 대소문자 | 콜레이션 의존(운영 기본은 무시) | 저장과 조회 전에 소문자로 정규화 | 로그인 시 대소문자 차이 처리 |
| 앞뒤 공백 | 저장됨 | 가입과 로그인 전에 `trim` | 같은 계정이 공백 차이로 중복될 수 있음 |
| 닉네임 대소문자 | 콜레이션 의존 | 콜레이션 정책을 그대로 따르거나 명시 | 표시 정책 |

- 정규화를 도입하면 기존 데이터의 중복 확인이 다시 필요하다. 그러므로 정책을 먼저 정하고, 운영 데이터 확인 뒤 적용한다.

## 5. 테스트 환경의 한계

- H2는 MySQL 모드로 실행되지만 **콜레이션 동작은 MySQL과 같지 않다.** 테스트는 제약이 존재하고 충돌을 메시지로 바꾸는 것만 확인한다.
- 대소문자·공백에 따른 중복 판정은 **MySQL에서 직접 확인하지 않았다.** 이 항목은 미확인이다.

## 6. 적용 절차 (운영)

1. 3장의 확인을 모두 통과한다.
2. 운영 DB 백업을 받는다.
3. `backend/db/migrations/2026-10-07-users-unique-keys.sql`을 실행한다(한 파일이며 다른 마이그레이션과 순서 의존 없음).
4. 실행 후 마지막 주석의 인덱스 조회로 `uk_users_email`, `uk_users_nickname`이 생겼는지 확인한다.
5. 가입 흐름을 실서버에서 한 번 확인한다.

**롤백**: `DROP INDEX uk_users_email`, `DROP INDEX uk_users_nickname`. 데이터는 변하지 않는다.
