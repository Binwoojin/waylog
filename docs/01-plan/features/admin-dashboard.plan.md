# admin-dashboard 계획 문서

> **요약**: `/admin` 하위에 관리자 전용 레이아웃(사이드바 + 대시보드 홈 + 리소스별 관리 화면)을 신설하고, 공지사항·여행코스·회원·피드 네 리소스를 한 곳에서 관리할 수 있게 한다. 공지사항은 이미 있는 백엔드 API를 소비하는 프론트 UI만 추가하고, 여행코스·회원·피드는 백엔드 스키마/API부터 새로 만든다.
>
> **프로젝트**: WayLog (React + Spring Boot 국내 여행 SNS)
> **버전**: frontend 0.0.0 / backend Spring Boot 4.1.0
> **작성자**: WOOJIN (Claude Code 보조)
> **작성일**: 2026-09-29
> **상태**: Approved (8장 사용자 결정 D-1 ~ D-7 반영, 2026-09-29)
> **근거**: 사용자 요청(2026-09-29, 관리자 대시보드 신설), `docs/01-plan/features/destination-list-integration.plan.md` D-1(여행코스 목록·상세 분리 결정)의 후속

## Executive Summary

| 관점 | 내용 |
|------|------|
| **문제** | WayLog에는 관리자가 서비스 데이터를 다룰 화면이 없다. 공지사항은 백엔드 API(`/api/v1/admin/notices`)만 있고 이를 쓰는 프론트가 없다. 여행코스·회원·피드는 관리자용 조회·변경 API 자체가 없다. `/api/v1/admin/**`은 이미 `ROLE_ADMIN`으로 보호돼 있지만 그 뒤에 아무 화면도 없는 상태다. |
| **해결** | `/admin` 전용 라우트·레이아웃·라우트 가드를 만들고, 리소스마다 목록/생성/수정/삭제 화면을 둔다. 공지사항은 기존 API를 그대로 소비한다. 여행코스는 이번에 스키마와 CRUD API를 새로 설계해, 이후 사용자용 여행코스 목록·상세 기능(destination-list-integration D-1의 후속)이 같은 스키마를 읽어 쓰게 한다. 회원·피드는 조회·상태 변경 위주의 신규 API를 최소로 추가한다. |
| **기능/UX 효과** | 관리자가 콘솔이나 DB 직접 조작 없이 공지·여행코스·회원·피드를 관리할 수 있다. 일반 사용자 화면과 분리된 레이아웃으로 오조작 위험을 줄인다. |
| **핵심 가치** | 역할 기반 라우트 가드(프론트 UX 가드 + 백엔드 최종 인가), 4개 리소스가 공유하는 관리자 UI 패턴(테이블·페이지네이션·폼·삭제 확인) 설계, 스키마를 먼저 정하고 관리자 화면 → 사용자 화면 순으로 점진 공개하는 API 설계를 면접에서 설명할 수 있다. |

## 1. 개요

### 1.1 목적

관리자가 로그인 후 `/admin` 하위의 별도 화면에서 공지사항·여행코스·회원·피드를 한곳에서 관리할 수 있게 한다. 일반 사용자 화면과 레이아웃·상태·API 권한을 분리해, 운영 기능이 커져도 사용자 화면 코드에 영향을 주지 않게 한다.

### 1.2 배경 (코드 확인 결과)

**인가 인프라 (이미 있음)**

| 구성 | 위치 | 내용 |
|------|------|------|
| 관리자 API 인가 | `SecurityConfig.java:69-70` | `/api/v1/admin/**` 전체가 `hasAuthority("ROLE_ADMIN")`로 보호됨 |
| 역할 계산 | `JwtAuthenticationFilter.java:66-73` | 요청마다 DB에서 `UserEntity.grade`를 다시 읽어 `ROLE_{GRADE}`로 변환. JWT 클레임이 아니라 DB 값을 그대로 쓰므로, 등급을 바꾸면 **다음 요청부터 즉시 반영**된다 |
| 로그인 응답의 role | `AuthController.java:44`, `authApi.js:11` | `login`/`refresh` 응답이 `member.role`을 이미 내려준다. 프론트가 별도 API 없이 `useAuth().member.role`로 관리자 여부를 판단할 수 있다 |
| 인증/인가 실패 구분 | `SecurityConfig.java:94-114` | 401(재인증 가능)과 403(권한 부족)을 구분해 내려준다. 비로그인 사용자가 `/admin/**`에 접근하면 401이다 |

즉 **백엔드 인가는 이미 완성돼 있고, 프론트 라우트 가드는 UX용 방어(잘못된 안내 없이 바로 리다이렉트)일 뿐 최종 방어선이 아니다.**

**리소스별 현재 상태**

| 리소스 | 백엔드 API | 프론트 관리자 UI | 비고 |
|--------|-----------|------------------|------|
| 공지사항 | 있음. `PostController`의 `GET/PATCH /admin/notices`, `POST /admin/notices`, `PUT /admin/notices/{id}`(멀티파트), `DELETE /admin/notices/{id}` | 없음 | 공개 조회 `GET /api/v1/notices`, `GET /api/v1/notices/{id}`도 이미 있고 `permitAll`(`SecurityConfig.java:56`). 사용자 화면의 `/notices`도 아직 `ComingSoonPage`라 완전히 새 기능은 아님 |
| 여행코스 | 없음(자체 스키마). `tour` 패키지의 코스 관련 코드(`TourCourseSearchSourceService`, `TourCourseResponse`, contentTypeId 25)는 **TourAPI 외부 코스 데이터를 그대로 캐시하는 프록시**이지 WayLog가 직접 등록하는 코스가 아님 | 없음 | 관리자가 직접 코스명·기간/테마·경유지·이미지를 입력하는 기능은 이 프록시와 무관한 **새 자체 도메인**이 필요하다 |
| 회원 | 없음. `UserController`에는 `check-email`/`check-nickname`만 있음(`UserController.java:20,31`) | 없음 | `UserEntity`(`UserEntity.java`)에는 `grade`만 있고 상태·정지 관련 컬럼이 없다 |
| 피드 | 부분적으로 있음. `FeedController`에 `GET /api/v1/feed/posts`(목록), `GET /{postId}`(상세), `DELETE /{postId}`가 이미 있음 | 없음 | `DELETE`는 `FeedService.delete(postId, email)` → `getOwnedPost`로 **작성자 본인만** 삭제 가능(`FeedService.java:198-199`). 관리자가 타인의 게시물을 지우려면 소유권 검사를 우회하는 **새 엔드포인트**가 필요하다 |

**공지사항 API의 구체적인 갭**

- `POST /admin/notices`(`PostController.java:49`)는 `PostCreateRequest{title, content, author}`만 받는다. 이미지 업로드 파라미터가 없다(멀티파트 버전은 주석 처리돼 있음, `:57-64`).
- `PUT /admin/notices/{id}`(`:66`)는 멀티파트로 `images` 추가와 `removeImageIds` 삭제를 지원한다(`PostUpdateRequest.java`).
- 그런데 조회 응답 `PostAdminResponse`(`PostAdminResponse.java`)에는 **이미지 필드가 없다.** 이번 범위는 이미지 관리를 포함하지 않기로 확정했으므로(D-6), 이 응답을 확장하지 않고 텍스트 공지만 지원한다.

## 2. 범위

### 2.1 포함 (1차 범위, 사용자 승인 완료)

- [ ] 관리자 공통 셸: `/admin` 라우트 가드, `AdminLayout`(사이드바 + 콘텐츠), 대시보드 홈
- [ ] 공지사항 관리 UI: 목록(검색·페이지네이션), 상세/수정, 생성, 삭제 — 기존 API 소비
- [ ] 여행코스 관리: 신규 스키마(코스명, 일자별 경유지 목록, 이미지) + CRUD API + 관리자 UI(목록, 생성, 수정, 삭제, 일자·경유지 편집)
- [ ] 회원 관리: 회원 목록 조회(검색·페이지네이션), 등급 변경, 활동 정지 상태 관리 — 신규 API + 관리자 UI
- [ ] 피드 관리: 게시물 목록 모니터링(기존 조회 API 재사용), 사유 구분 삭제(일반/정책위반), 정책위반 시 작성자 활동 정지 연동 — 신규 API + 관리자 UI

### 2.2 제외 (이번 범위 아님)

- 게시판/댓글 신고 관리 (다음 단계로 보류, 사용자 확정)
- 여행코스·회원·피드 각각의 **공개(사용자용) 조회 API**와 사용자 화면 전환. 이번 기능은 관리자 CRUD까지만 다루고, 사용자용 여행코스 목록·상세는 이 기능이 만드는 스키마를 전제로 한 **별도 후속 기능**으로 남긴다 (4장)
- 지도 API 연동(주소 검색, 좌표 선택 UI). 여행코스 경유지의 좌표는 이번에는 숫자/텍스트 입력으로만 받는다. 다만 스키마는 이 연동을 나중에 막지 않는 형태로 설계한다(D-1)
- 공지사항 이미지 관리(기존 이미지 표시, 첨부·삭제 UI). 이번 범위는 텍스트 공지만 지원한다(D-6)
- 회원 탈퇴, 소셜 로그인 연동, 권한 세분화(예: 서브 관리자 등급)
- 여행코스·회원·피드에 대한 감사 로그(누가 언제 무엇을 바꿨는지) UI. 백엔드에 최소 로그만 남기고 조회 화면은 이번 범위 밖
- 대시보드 홈의 통계/차트(가입자 추이, 신고 추이 등). 1차는 리소스 진입 카드 수준

| FR-C01 | 여행코스 스키마를 3단 구조로 설계한다: **코스**(코스명, 테마, 대표 이미지) → **일자(Day)**(순서, 코스에 속함) → **경유지(Stop)**(순서, 일자에 속함). 경유지는 `참조 방식(REFERENCE)` — TourAPI `contentId`+`contentTypeId` — 와 `직접 입력(CUSTOM)` — 명칭+주소+좌표(숫자 입력) — 두 방식을 모두 저장할 수 있는 구조로 만든다. 이는 확정 사양이 아니라 **향후 지도 API 연동으로 TourAPI에 없는 임의 장소를 경유지로 등록하는 확장을 막지 않기 위한 설계 제약**이다(D-1). 이번 기능은 좌표 입력 UI 자체(지도 검색 등)는 만들지 않는다(2.2) | High | frontend-support-backend | 신규 |

| FR-C03 | 경유지 이미지 업로드는 기존 `S3StorageService`(board/feed에서 이미 쓰는 패턴)를 재사용한다. **같은 일자(Day)에 속한 모든 경유지의 이미지 수 합계가 10장을 넘지 않도록 서버에서 검증한다**(코스 전체 제한이 아니라 일자 단위 제한, D-3). 코스 목록 카드에 쓸 대표 이미지를 경유지 이미지와 별도로 둘지는 설계 문서에서 확정한다 | High | frontend-support-backend | 신규 |
| FR-C04 | 관리자 코스 목록/생성/수정/삭제 화면을 만든다. 생성·수정 화면은 일자 추가/삭제와 일자별 경유지 편집을 함께 제공한다 | High | frontend-lead | 신규 |
| FR-C05 | 경유지 편집 UI를 만든다. 경유지를 추가할 때 "기존 여행지 카탈로그에서 검색해 참조"와 "직접 입력(명칭·주소·좌표)" 두 방식을 모두 제공한다(D-1). 참조 방식은 기존 목록 기능(`useTourList`, 검색 모달)의 선택 모드 재사용을 검토한다. 경유지는 일자 내에서, 그리고 일자 간에도 순서를 옮길 수 있어야 한다 | High | frontend-lead | 신규 |
| FR-C06 | 코스 생성/수정 폼에 검증을 둔다: 코스명 필수, 최소 일자 1개, 일자당 최소 경유지 1개, **일자당 이미지 합계 10장 이하**(D-3). 저장 중 상태를 표시한다 | Medium | frontend-lead | 신규 |

### 3.4 회원 관리 (완전 신규)

이번 기능의 "회원 제재"는 회원 리소스 자체의 일반 정지 기능이 아니라 **피드(SNS) 정책위반 대응의 일부**다(D-4). 회원 쪽에는 상태를 담을 컬럼만 추가하고, 실제 제재 트리거는 3.5절 피드 관리에 있다.

| ID | 요구사항 | 우선순위 | 담당 | 신규/기존 |
|----|----------|----------|------|-----------|
| FR-U01 | `UserEntity`에 활동 정지 상태 컬럼(정지 여부, 사유, 정지 일시, 해제 일시)을 추가한다. 이 상태는 피드 정책위반 삭제(FR-F03)에서 트리거되거나, 회원 관리 화면에서 관리자가 직접 설정할 수도 있다(D-4) | High | frontend-support-backend | 신규 |
| FR-U02 | 관리자 회원 목록 API(`GET /api/v1/admin/users`, 검색·페이지네이션, 비밀번호 해시 등 민감정보 제외)를 만든다 | High | frontend-support-backend | 신규 |
| FR-U03 | 등급 변경 API(`PATCH /api/v1/admin/users/{id}/grade`)를 만든다. 변경 즉시 다음 요청부터 반영됨(JwtAuthenticationFilter가 매 요청 DB 조회, 1.2절) | High | frontend-support-backend | 신규 |
| FR-U04 | 활동 정지 API(`PATCH /api/v1/admin/users/{id}/suspension` 등)를 만든다. 피드 관리 화면(FR-F04)과 회원 관리 화면 양쪽에서 호출할 수 있는 공용 API로 만든다. 정지 상태가 로그인 자체를 막는지, 글쓰기 등 특정 행위만 막는지, 기간제인지는 세부 사항이라 설계 문서에서 확정한다 | High | frontend-support-backend | 신규 |
| FR-U05 | 관리자 회원 목록/상세 화면(등급 배지, 활동 정지 상태·사유 표시, 등급 변경 폼, 정지/해제 폼)을 만든다 | High | frontend-lead | 신규 |
| FR-U06 | 관리자가 자기 자신의 등급을 낮추거나 자신을 정지시키는 것을 막는다(운영 사고 방지) | Medium | frontend-support-backend | 신규 |

삭제 방식은 사유에 따라 소프트/하드로 나뉜다(D-5). 정책위반 삭제는 회원 활동 정지(3.4절)와 연결된다(D-4).

|----|----------|----------|------|-----------|
| FR-F01 | 관리자 피드 목록 화면에서 `GET /api/v1/feed/posts`(기존, 공개 조회 API 재사용)로 게시물을 모니터링한다 | High | frontend-lead | 기존 API |

| FR-F05 | 관리자 피드 목록에 작성자·내용 일부·이미지 수·좋아요/댓글 수·삭제 상태(정상/소프트 삭제·사유)를 표시하고, 상세로 이동해 전체 내용을 확인할 수 있게 한다 | Medium | frontend-lead | 신규 |
| FR-F06 | 삭제 확인 모달(사유·유형 선택 포함)과 삭제 후 피드백(토스트 등)을 제공한다 | Medium | frontend-lead | 신규 |

## 4. 여행코스 리소스의 의존관계와 작업 순서

`destination-list-integration.plan.md`의 D-1(2026-09-28)은 "여행코스 카드는 경유지가 없고, 탭은 기간이 아닌 테마 기준이며, 상세는 백엔드 신규 API가 필요해 범위가 두 배가 된다"는 이유로 여행코스 목록·상세 전환을 다음 기능으로 미뤘다. `/destinations/courses`는 지금도 `destinationMocks.js` 목업을 그대로 쓴다(`App.jsx:297`).

이번 admin-dashboard 기능이 그 "신규 백엔드 API"의 출발점이 된다. 다만 **관리자가 채우는 스키마와 사용자가 읽는 스키마는 같아야 하므로, 두 기능은 다음 순서로 진행해야 한다.**

1. **이번 기능(admin-dashboard)**: 여행코스 스키마를 설계하고, 관리자 전용 CRUD API(`/api/v1/admin/courses`)와 관리자 UI를 만든다. 경유지 모델(D-1)과 기간 구조(D-2)는 이미 결정됐으므로, 설계 문서에서는 이 결정을 3.3절 FR-C01의 3단 구조(코스-일자-경유지)와 REFERENCE/CUSTOM 두 경유지 타입으로 구체화한다. 확정된 스키마는 그대로 후속 기능의 계약이 된다.
2. **후속 기능(가칭 `tour-course-list-integration`, 이번 범위 밖)**: 이번에 만든 스키마를 읽는 **공개 조회 API**(`GET /api/v1/courses`, `GET /api/v1/courses/{id}` 등, `permitAll`)를 추가하고, `DestinationCatalogPage`(kind="course")와 `TravelCourseDetailPage`를 목업에서 이 API로 전환한다. destination-list-integration이 관광지·문화시설에서 했던 것과 같은 전환(목업 → API, URL 상태, 로딩/에러/빈 상태)을 여행코스에도 적용한다. 이 기능은 REFERENCE 타입 경유지를 여행지 상세로 링크할 수 있지만, CUSTOM 타입 경유지(좌표만 있는 임의 장소)는 지도 API 연동 전까지 이름·주소 텍스트로만 보여준다.

**순서를 바꿀 수 없는 이유**: 사용자용 목록·상세 기능은 "무엇을 보여줄지"가 아니라 "이미 존재하는 데이터를 어떻게 보여줄지"를 다루는 기능이라, 데이터가 없으면 시작할 수 없다. 반대로 관리자 CRUD는 사용자 화면 없이도 독립적으로 완성하고 검증할 수 있다(관리자 화면 자체에서 등록·조회가 되는지 확인 가능).

**설계 제약으로서의 D-1**: D-1은 "경유지는 REFERENCE 또는 CUSTOM 중 하나로 확정"이 아니라 "두 방식을 처음부터 함께 지원하는 스키마로 만들라"는 제약이다. 지도 API 연동(주소 검색, 좌표 선택 UI)은 이번 범위가 아니지만(2.2), 스키마에서 CUSTOM 경유지의 좌표·주소·명칭 필드를 미리 마련해 두면 그 연동은 입력 UI만 추가하는 작업이 되고 스키마 변경이 필요 없다.

**이번 기능에서 반드시 남겨야 할 것**: 스키마 결정 근거(D-1~D-3)와 API 응답 계약(코스-일자-경유지 중첩 구조, REFERENCE/CUSTOM 필드)을 설계 문서(`admin-dashboard.design.md`)에 명시해, 후속 기능이 별도 조사 없이 바로 공개 API를 얹을 수 있게 한다.

## 5. 프론트엔드 아키텍처 고려사항

### 5.1 라우트 가드

- `RequireAdmin` 컴포넌트(또는 라우트 wrapper)를 만들어 `/admin/*` 라우트를 감싼다. `useAuth()`의 `member`, `isRestoring`을 그대로 재사용한다.
  - `isRestoring === true`: 판단 보류, 로딩 표시 (새로고침 직후 깜빡임 방지, 기존 `AuthContext` 패턴과 동일).
  - `member === null`: `/login`으로 리다이렉트.
  - `member.role !== 'ADMIN'`: 접근 거부 화면(관리자 전용 안내).
- 이 가드는 **UX 보조**다. 실제 방어는 이미 `SecurityConfig`가 하고 있으므로(1.2절), 프론트 가드가 뚫려도 API 자체가 403을 반환한다. 이 이중 방어 구조(클라이언트 가드 + 서버 인가)를 설계 문서와 포트폴리오 자료에 명시한다.

### 5.2 레이아웃 구조

- 신규 `AdminLayout`(사이드바 내비게이션 + 콘텐츠 `Outlet`)을 만들고, 기존 사용자용 `Layout`(헤더/푸터, `components/layout/Layout.jsx`)과는 별도 트리로 둔다. 관리자 화면에 일반 사용자 헤더·검색·로그인 버튼이 노출될 이유가 없다.
- 사이드바 메뉴는 리소스 단위(공지·여행코스·회원·피드)로 고정하고, 각 리소스는 `목록 → 상세/폼`의 중첩 라우트를 가진다.

### 5.3 상태 관리

| 상태 | 위치 | 이유 |
|------|------|------|
| 관리자 인증 여부(`member.role`) | 기존 `AuthContext` | 이미 있는 전역 상태를 재사용. 새 Context를 만들 이유가 없다 |
| 리소스 목록의 검색어·페이지 | URL(`useSearchParams`) | destination-list-integration에서 이미 검증된 패턴(뒤로 가기 복원, 공유 가능한 URL)을 그대로 따른다 |
| 리소스 목록/상세 서버 상태 | 커스텀 훅(`useAdminNoticeList`, `useAdminCourseList` 등, `useTourList`/`useTourDetail`과 같은 패턴) | 프로젝트에 서버 상태 라이브러리(TanStack Query 등)가 없고, tour-detail-integration에서 이미 "새 의존성 없이 커스텀 훅"으로 결정한 전례가 있다(§7.2 일관성 유지). 관리자 화면이라 트래픽이 적어 캐싱·재검증 요구가 낮다는 점도 근거다 |
| 생성/수정 폼 상태 | 로컬 `useState`, 이미지가 있으면 `FormData` | 기존 프로젝트에 폼 라이브러리가 없다. 관리자 폼은 화면 수가 제한적이라 새 의존성 도입 근거가 약하다 |

### 5.4 재사용 vs 신규

- 공용 테이블/페이지네이션/삭제 모달(FR-D04)은 4개 리소스가 공유해, 리소스가 늘어나도 반복 구현을 막는다. 다만 리소스마다 폼 필드는 다르므로 폼 자체는 공용화하지 않는다(과도한 추상화 방지).
- 여행코스 경유지의 REFERENCE 입력(기존 여행지 참조, D-1)은 `useTourList`와 검색 모달의 선택 로직을 재사용할 수 있는지 설계 단계에서 검토한다. CUSTOM 입력(직접 입력)은 별도의 간단한 폼(명칭·주소·좌표)으로 만든다.

| 여행코스 | 신규 도메인 패키지, 엔티티 3종(코스, 일자, 경유지 — 경유지는 REFERENCE/CUSTOM 구분 필드 포함), 리포지토리, 서비스, `/api/v1/admin/courses` CRUD 컨트롤러, 일자당 이미지 10장 제한 검증(D-3) | 담당: frontend-support-backend. 후속 기능(4장)이 이 스키마를 공개 API로 감싸므로, 응답 필드 이름 등은 신중히 정한다 |
| 회원 | `UserEntity` 활동 정지 컬럼 추가(마이그레이션: 정지 여부, 사유, 정지/해제 일시), `GET/PATCH /api/v1/admin/users` 계열, 활동 정지 API(`PATCH .../suspension`). 정지의 정확한 적용 범위(로그인 차단 여부 등)는 설계 문서에서 확정 | 담당: frontend-support-backend |
| 피드 | `FeedPost`에 소프트 삭제 컬럼(삭제 여부/일시, 사유, 유형) 추가, `DELETE /api/v1/admin/feed/posts/{id}` 신규 엔드포인트(사유/유형 파라미터, 일반=소프트/정책위반=하드, 소유권 검사 우회는 관리자 인가로 대체), 정책위반 삭제 시 회원 활동 정지 API 연계 호출(D-4, D-5) | 담당: frontend-support-backend |

모든 신규 관리자 API는 `/api/v1/admin/**` 아래 두어 `SecurityConfig`의 기존 `hasAuthority("ROLE_ADMIN")` 규칙을 그대로 상속받는다(별도 인가 설정 불필요).

## 7. 성공 기준

### 7.1 완료 조건

- [ ] 비관리자(비로그인 포함)는 `/admin` 어떤 하위 경로로도 실제 데이터에 접근하지 못한다(프론트 가드 + 백엔드 403 모두 확인)
- [ ] 관리자는 사이드바에서 공지·여행코스·회원·피드 관리 화면으로 이동할 수 있다
- [ ] 공지사항: 목록 조회, 생성, 수정, 삭제가 실제 API로 동작한다
- [ ] 여행코스: 관리자가 코스명·테마·일자별 경유지(참조/직접 입력 모두)·이미지(일자당 10장 이하)를 등록·수정·삭제할 수 있고, 스키마가 §4의 후속 기능이 그대로 쓸 수 있는 형태로 문서화돼 있다
- [ ] 회원: 목록 조회, 등급 변경, 활동 정지/해제가 동작하고 변경이 다음 요청부터 즉시 반영된다(재로그인 불필요)
- [ ] 피드: 목록 모니터링, 일반 삭제(소프트)·정책위반 삭제(하드) 구분, 정책위반 삭제 시 작성자 활동 정지 연동이 동작하고, 일반 사용자의 피드 조회·삭제(본인) API에 회귀가 없다
- [ ] frontend-code-reviewer 리뷰와 bkit gap 분석 완료

### 7.2 품질 기준

- [ ] `npm run lint` 오류 0, `npm run build` 성공
- [ ] 백엔드 `mvnw clean test` 통과, 신규 관리자 API는 curl 또는 단위 테스트로 인가(403/401)와 정상 동작을 확인
- [ ] gap 분석 Match Rate 90% 이상

## 9. 작업 분담과 권장 진행 순서 (CLAUDE.md bkit 협업 규칙)

```
frontend-lead            : 프론트 전체 (공통 셸 + 4개 리소스 화면)
frontend-support-backend : 여행코스 신규 API, 회원 신규 API(활동 정지 포함), 피드 신규 삭제 API(소프트/하드 + 활동 정지 연계)
frontend-code-reviewer   : 구현 후 리뷰
bkit gap-detector         : 설계 대비 gap 분석
frontend-interview-coach : 완료 보고서 후 포트폴리오 자료 추출
```

D-7 결정에 따라 4개 리소스는 **하나의 PDCA**로 진행한다. 다만 리소스별 위험도와 백엔드 준비 상태가 크게 달라, 같은 PDCA 안에서도 다음 구현 순서를 권장한다:

1. **관리자 공통 셸** — 라우트 가드·레이아웃·공용 UI(FR-D01~05)를 먼저 완성해 이후 리소스 화면이 이 위에서 조립되게 한다.
2. **공지사항** — 백엔드가 이미 있어 가장 빠르게 끝까지(생성~삭제) 검증할 수 있다. 공통 셸이 실전 데이터로 동작하는지 확인하는 역할도 겸한다.
3. **회원 관리(활동 정지 컬럼·API)** — 피드 관리가 이 API를 호출하므로(FR-F04), 피드보다 먼저 최소한 FR-U01·FR-U04(활동 정지 스키마·API)까지는 준비돼 있어야 한다.
4. **피드 관리** — 조회 API는 이미 있고, 소프트 삭제 컬럼(FR-F02)과 사유 구분 삭제 API(FR-F03), 회원 활동 정지 연동(FR-F04)을 더한다.
5. **여행코스** — 범위가 가장 크고 D-1~D-3 결정을 3단 스키마(코스-일자-경유지)로 구체화하는 설계 작업과 후속 기능(4장)의 계약을 겸하므로, 하나의 PDCA 안에서도 가장 마지막에, 가장 넉넉한 Design 검토를 거쳐 진행한다.

백엔드와 프론트는 리소스별로 파일이 겹치지 않으므로 병렬 진행이 가능하다. 단, 같은 리소스 안에서는 API 계약(요청/응답 필드)이 먼저 확정된 뒤 프론트 화면을 붙이고, 회원의 활동 정지 API(3순위)는 피드 연동(4순위) 이전에 계약이 확정돼야 한다. 같은 파일을 여러 구현 에이전트가 동시에 수정하지 않는다.
