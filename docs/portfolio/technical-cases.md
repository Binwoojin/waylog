## 사례 1. 인증 토큰 보관·세션 복원과 재발급 경쟁 조건

### 문제
- 로그인 응답의 Access Token이 프론트에서 버려져 보호 API를 호출할 수 없었다.
- 새로고침하면 로그인 상태가 사라졌다.
- 여러 요청이 동시에 401을 받으면 재발급이 여러 번 일어날 수 있었다.
- 로그아웃 직후 도착한 이전 응답이 로그인 상태를 되살릴 수 있었다.
- 인증 복원이 끝나기 전에 보호 API를 호출하면 Authorization 없이 나가 401을 받았다.

### 원인
- 토큰을 저장하고 요청에 붙이는 경로가 없었다.
- 재발급 요청을 하나로 묶는 장치가 없었다.
- 요청이 어떤 인증 상태에서 나갔는지 기록하지 않아, 응답이 늦게 도착했을 때 현재 상태와 비교할 수 없었다.
- 세션 복원과 화면 데이터 요청의 순서를 맞추지 않았다.

### 대안
| 선택지 | 장점 | 단점 |
|---|---|---|
| 메모리에 Access Token 보관 (선택) | 웹 스토리지에 토큰이 남지 않는다 | 새로고침 시 소실, 복원 로직 필요 |
| sessionStorage / localStorage | 구현이 단순하다 | 같은 출처 스크립트가 읽을 수 있다 |
| 재발급을 요청마다 각자 수행 | 구현이 단순하다 | 동시 401에서 재발급이 중복된다 |
| 재발급 Promise 공유 (single-flight, 선택) | 동시 401이 재발급 1회로 합쳐진다 | 공유 상태 관리가 필요하다 |

### 선택 이유
- 토큰을 웹 스토리지에 두지 않으면 같은 출처 스크립트가 저장소에서 토큰을 읽는 경로가 없다. 다만 페이지 안에서 실행되는 XSS 자체를 막는 것은 아니다.
- 새로고침 후 복원은 HttpOnly 리프레시 쿠키로 `/auth/refresh`를 호출해 처리한다.
- 요청 시점의 인증 세대 번호를 캡처하면, 응답이 늦게 와도 현재 세대와 다르면 결과를 무시하거나 재시도할 수 있다.
- 복원이 끝날 때까지 개인화 데이터 요청을 보류한다.

### 구현 근거
- `frontend/src/api/client.js:25-31` — `authGeneration` 번호와 `refreshPromise`(single-flight)
- `frontend/src/api/client.js:53, 106, 116, 121` — 요청 시점 세대 번호 캡처, 세대가 바뀌었으면 현재 토큰으로 재시도하거나 세션 만료 처리를 건너뛴다
- `frontend/src/context/AuthContext.jsx:37` — `isRestoring` 상태
- `frontend/src/hooks/useTourBookmarks.js:26-28, 54` — 복원 전에는 요청하지 않고, `isRestoring`과 `memberId`가 deps에 있다
- `frontend/src/pages/TravelDetailPage.jsx:51, 60` — `memberId`를 상세 컴포넌트 key에 넣어 로그인 사용자가 바뀌면 상세 전체를 다시 그린다
- 백엔드: 401은 재인증 필요, 403은 권한 없음으로 구분한다(`SecurityConfig`, `AuthService`)

### 검증
- **실서버 기반**: 가입 직후 로그인(S1b), 새로고침 후 세션 유지(S2)는 실서버 브라우저 검증에서 통과했다(`docs/validation/2026-10-07-live-validation.md`).
- **실서버 기반 이전 라운드**: 로그아웃 후 상세 화면에서 "저장됨"이 사라지고, 재로그인 시 복원되는 흐름을 실서버 계정으로 확인했다(이전 라운드 C11).
- **자동 테스트**: `AuthAccountHttpFlowTest`(로그인, refresh, 정지·탈퇴 차단 10개 HTTP 테스트).

### 한계
- 메모리 보관은 저장소 기반 토큰 노출을 줄이는 것이지, 페이지 내 XSS를 막지 않는다.
- 복원 요청이 네트워크 오류로 실패하면 로그인 사용자의 상세 화면 "저장" 상태가 조용히 틀릴 수 있다. 이 한계는 주석에 명시했고 아직 수정하지 않았다.
- 비로그인 방문자도 복원 응답을 기다리므로 상세 로딩이 `/auth/refresh` 왕복만큼 늦는다.
- 인증·DB 최종 변경분의 독립 리뷰는 완료했다(`docs/validation/2026-10-07-independent-review-auth-db.md`).

## 사례 2. 관광 검색·상세의 실제 API 연동과 비동기 UI

### 문제
- 여행지 메인, 즐길거리 허브, 카테고리 페이지가 하드코딩된 목업 데이터로 동작했다. 같은 항목을 45장으로 복제하거나 동작하지 않는 필터 버튼이 있었다.
- 존재하지 않는 상세 주소가 엉뚱한 목업 항목으로 대체되었다.
- 카테고리나 필터를 빠르게 바꾸면 이전 요청의 결과가 나중에 도착해 화면을 덮을 수 있었다.
- 없는 콘텐츠를 조회하면 404가 아니라 502로 보였다.

### 원인
- 페이지마다 데이터를 따로 두었고, 공통 조회 계층이 없었다.
- 요청에 취소 신호가 없어, 오래된 응답을 무시하지 못했다.
- TourAPI는 결과가 없을 때 `items`를 객체가 아닌 빈 문자열로 내려주는데, 역직렬화가 이 형태를 처리하지 못해 외부 장애(502)로 분류되었다.

### 대안
| 선택지 | 장점 | 단점 |
|---|---|---|
| 서버 상태 라이브러리 도입 | 캐시와 재시도가 내장되어 있다 | 새 의존성이 생긴다. 현재 범위에 과하다 |
| 페이지마다 fetch 직접 작성 | 구현이 빠르다 | 취소와 경쟁 처리가 페이지마다 달라진다 |
| 공통 훅으로 요청 키와 취소 처리 (선택) | 의존성 추가 없이 경쟁 처리를 한 곳에 둔다 | 캐시와 재시도는 직접 관리해야 한다 |
| 목업 상세를 남기고 표시만 바꿈 | 화면은 유지된다 | 실제 데이터가 아닌 정보가 계속 보인다 |
| 목업 상세를 404로 처리 (선택) | 실제 콘텐츠만 남는다 | 목업 상세 화면이 사라진다 |

### 선택 이유
- 의존성을 늘리지 않고, 요청 키(쿼리 키와 재시도 횟수)가 바뀔 때만 재요청하고 이전 요청은 취소하는 구조를 택했다.
- 목업 상세는 배포 전 목업 페이지를 남기지 않는다는 결정에 따라 제거했다.
- 빈 `items` 문자열은 역직렬화 단계에서 빈 목록으로 받고, 클라이언트 계층에서 404로 매핑했다.

### 구현 근거
- `frontend/src/hooks/useTourList.js:34` — `requestKey = queryKey#attempt`
- `frontend/src/hooks/useTourList.js:39` — 요청에는 그 렌더의 최신 query를 사용
- `frontend/src/hooks/useTourDetail.js:40-59` — `isActive` 가드와 cleanup
- `backend/src/main/java/.../tour/dto/external/TourApiDetailCommonRawResponse.java`, `TourApiDetailIntroRawResponse.java` — 빈 문자열 `items`를 빈 목록으로 역직렬화
- `backend/src/main/java/.../tour/exception/TourExceptionHandler.java` — 없는 콘텐츠 404
- 상세 목업 제거 커밋 `e393f9c`, 404 수정 커밋 `d62a809`

### 검증
- **자동 테스트**: 프론트 순수 로직 테스트 182개(`tourListQuery`, `enjoyListQuery`, `courseListQuery`, `tourApi` 매퍼 등). 백엔드 `TourDetailNotFoundHttpTest`, `TourApiClientImplDetailTest`, `TourApiRawItemsDeserializationTest`(빈 응답과 객체 응답 모두 확인).
- **실서버 기반**: 없는 콘텐츠 조회가 `404 TOUR_CONTENT_NOT_FOUND`를 반환하는 것을 직접 호출과 프록시 호출 모두에서 확인했다.
- **실서버 기반 이전 라운드**: 필터와 URL 동기화, 페이지 이동, 상세 뒤로가기 후 필터 유지, 빠른 카테고리 전환 시 이전 카드가 남지 않는 흐름을 실서버에서 확인했다.

### 한계
- 성능 수치(로딩 시간, 요청 수)는 측정하지 않았다.
- 캐시와 재시도는 직접 구현하지 않았다. 서버 상태 라이브러리 도입과 비교한 결정은 기록으로만 남겼다.
- 두 상세 페이지의 중복 코드는 아직 공용 훅으로 묶지 않았다.
- 여행지 상세 화면의 지도 기능은 구현하지 않았다. 해당 자리는 제거했다.

## 사례 3. 북마크·댓글 상태 정합성과 회귀 테스트

### 문제
- 같은 항목을 빠르게 두 번 누르면 두 응답이 역순으로 도착해 화면과 서버 상태가 어긋날 수 있었다.
- 토글 요청이 실패하면 화면이 조용히 되돌아가, 사용자가 이유를 알 수 없었다.
- 목업 항목의 저장 버튼이 서버에 북마크를 만들었다. 목록에서 다시 열 수 없는 항목이었다.
- 댓글 수가 실제 댓글 개수와 어긋날 수 있는 구조였다.
- 공유 캐시에 사용자별 북마크 값을 넣으면 다른 사용자에게 값이 새어 나갈 수 있었다.

### 원인
- 토글 요청에 키별 진행 상태가 없어서, 같은 항목의 요청이 겹쳐도 막히지 않았다.
- 실패 처리와 안내 문구가 분리되어 있지 않았다.
- 댓글 수를 엔티티 로드 후 증감하면 동시 요청에서 값이 어긋날 수 있다.
- 캐시된 조회 결과에 요청자별 값을 함께 저장했다.

### 대안
| 선택지 | 장점 | 단점 |
|---|---|---|
| 요청 중 버튼만 비활성화 | 구현이 단순하다 | 다른 인스턴스의 중복 요청을 막지 못한다 |
| 키별 pending 가드와 낙관적 갱신 (선택) | 같은 항목의 중복 요청을 모든 인스턴스에서 막는다 | 롤백과 키 해제 경로를 정확히 맞춰야 한다 |
| 댓글 수를 조회 때마다 재계산 | 항상 정확하다 | 목록 조회 비용이 커진다 |
| 댓글 수를 DB에서 단일 UPDATE로 증감 (선택) | 동시 요청에서도 증감이 한 문장으로 처리된다 | 엔티티 캐시와의 동기화를 직접 고려해야 한다 |
| 캐시에 요청자별 값 저장 | 구현이 단순하다 | 다른 사용자에게 값이 새어 나간다 |
| 캐시에는 기본값 저장 후 요청자별 복사본 반환 (선택) | 공유 캐시에 개인 값이 남지 않는다 | 응답마다 복사 비용이 든다 |

### 선택 이유
- 낙관적 갱신은 화면을 즉시 바꾸고, 실패하면 이전 값으로 되돌리며 안내 문구를 보여준다. 키별 가드로 같은 항목의 요청이 겹치지 않게 한다.
- 댓글 수 UPDATE는 DB 단일 문장으로 처리한다. 처음에는 `clearAutomatically`를 붙였는데, 아직 반영되지 않은 삭제 예약까지 지워서 댓글이 실제로 삭제되지 않는 문제가 로컬 테스트에서 확인되어 옵션을 제거했다.
- 캐시에는 개인화되지 않은 기본값을 저장하고, 컨트롤러에서 요청자별 불변 복사본을 만든다.

### 구현 근거
- `frontend/src/lib/optimisticToggle.js:32, 36-49` — `pendingKeys` 가드, 키 해제는 `finally`에서 수행
- `frontend/src/pages/TravelDetailPage.jsx:107` — 저장 토글을 `runOptimisticToggle`로 감쌈, 실패 안내 문구 표시
- `backend/src/main/java/.../feed/repository/FeedPostRepository.java:24-30` — `@Modifying` 단일 UPDATE로 `commentCount` 증감
- `backend/src/main/java/.../feed/service/FeedCommentService.java:87, 114` — 생성 시 +1, 삭제 시 1 + 답글 수만큼 감소
- `backend/src/main/java/.../tour/bookmark/` — 개인화 테스트 `TourBookmarkPersonalizationTest`
- 프론트 수정 커밋 `b95e33a`(취소된 요청 무시, StrictMode 가드), 순수 로직 결함 수정 `100ac62`(optimistic apply 실패 시 키 해제)

### 검증
- **자동 테스트**: `optimisticToggle` 9개 케이스(중복 요청 차단, 롤백, apply 실패 시 키 해제). `FeedCommentServiceTest` 8개(생성·삭제 시 개수 증감, 답글, 게시글 삭제 연쇄). `TourBookmarkPersonalizationTest` 6개(캐시 격리). `TourBookmarkHttpFlowTest` 4개(토큰 없는 토글 401, 저장·해제 토글, 목록 조회).
- **실서버 기반**: 북마크 저장 → 새로고침 유지 → 목록 노출 → 해제(S3, S3b). 댓글 작성 0→1, 삭제 1→0(S4b, S4c). 타인 계정의 삭제 요청 403(S5a, S5b).
- **지연 주입 기반 (모킹)**: 응답을 1초 늦춘 상태에서 더블 클릭해도 토글 요청이 1회만 나가는 것을 확인했다. 실서버 지연이 아니다.

### 한계
- 댓글 수의 HTTP 수준 검증은 서비스 테스트 중심이다. 댓글 작성과 삭제가 연속으로 일어나는 HTTP 시나리오 테스트는 없다.
- 낙관적 갱신의 롤백 경로를 실서버 장애 상황에서 재현하지는 않았다.
- 피드 북마크의 목록 조회 성능(사진 N+1)은 기존 패턴 그대로이며 개선하지 않았다.
- 인증·DB 최종 변경분의 독립 리뷰는 완료했다(`docs/validation/2026-10-07-independent-review-auth-db.md`).

## 공통 한계

- 인증·DB 최종 변경분은 독립 리뷰를 완료했다(Must 1건 수정). 그 밖의 변경분은 각 사례의 검증 기록을 따른다.
- 운영 DB 스키마와 마이그레이션 적용 여부를 확인하지 못했다.
- 약관 이력 저장(버전, 동의 시각, 마케팅 동의 보존)은 구현하지 않았다. 현재는 필수 동의만 검증한다.
- 운영 SMTP 발송 안정성은 검증하지 않았다.
- 성능 수치는 측정하지 않았다.
