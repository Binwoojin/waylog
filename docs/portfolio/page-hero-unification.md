## Overview

두 페이지는 "안내 문구 → 제목 → 설명 → 검색 버튼 → 검색 도움말 + 비주얼"이라는 같은 골격을 쓰면서도 마크업과 모바일 CSS를 따로 가지고 있어, 모바일에서 정렬·배치 방식이 서로 달라져 있었다(`PageHero.jsx` JSDoc). 골격과 모바일 규칙을 `PageHero` 컴포넌트와 `PageHero.css` 한곳으로 모으고, 페이지별 문구·비주얼은 props로, 데스크톱·태블릿 세부 치수는 761px 이상으로 한정한 수정자 클래스로 남겼다. 두 번째 커밋에서는 모바일 비주얼 높이와 콜라주 축소 배율을 **단위 없는 CSS 변수 하나**에서 함께 계산하도록 정리했다.

## Background (커밋 `f9fa909` 이전 모바일 상태, diff 기준)

| 항목 | 여행지 `.destination-hero` | 여행 즐기기 `.enjoy-hero` |
|------|---------------------------|---------------------------|
| 히어로 높이 | `min-height: 760px` 고정 | `min-height: 770px` 고정 |
| 배치 | `flex` 세로, 가운데 정렬 | `display: block` |
| 비주얼 | 문서 흐름 안 `img`, `height: 280px` | 콜라주를 `position: absolute; bottom: 15px`에 두고 `scale(.57)` |
| 제목 크기 | `47px` | `48px` |
| 안내 문구 아래 여백 | `26px` | `28px` |
| 설명 크기 | `19px` | `20px` |
| 도움말 크기 | `13px` | `14px` |

- 같은 역할의 요소가 1 ~ 2px씩 다르고, 한쪽은 흐름 안 배치, 다른 쪽은 절대 위치였다.
- 여행 즐기기 쪽은 비주얼이 절대 위치라서 히어로 높이를 고정값으로 잡아야 했다. `PageHero.css` 주석은 비주얼을 흐름 안에 두는 이유를 "제목이 여러 줄로 늘어나도 서로 겹치지 않고, 고정 min-height 대신 위아래 여백으로 높이를 콘텐츠에 맞추기 위해"라고 적는다.
- *주의*: 이전 상태에서 제목과 콜라주가 실제로 겹친 것을 측정한 기록은 없다. 위 내용은 구조상 위험을 코드 주석으로 남긴 것이다.

## 1. 포트폴리오 프로젝트 설명용 문단

WayLog의 여행지·여행 즐기기 페이지는 같은 히어로 구조를 각자 다른 마크업과 CSS로 구현하고 있어 모바일에서 정렬과 배치가 서로 달랐습니다. 공통 골격과 모바일 규칙을 `PageHero` 컴포넌트로 추출하고, 페이지별 차이는 문구·비주얼 props와 데스크톱 전용 수정자 클래스로만 남겼습니다. 수정자 규칙(선택자 우선순위 0,2,0)이 모바일 공통 규칙(0,1,0)을 덮어쓰지 않도록 수정자는 `@media (min-width: 761px)` 안에만 두는 규칙을 정해 JSDoc과 CSS 주석에 적었습니다. 모바일에서는 `transform: scale()`이 레이아웃 크기를 줄이지 않는 문제를 흐름 안의 고정 높이 상자로 풀고, 상자 높이와 콜라주 축소 배율을 단위 없는 CSS 변수 하나(`--page-hero-visual-h`)에서 함께 계산하게 해 두 값이 따로 어긋나지 않게 했습니다.

## 2. 이력서 bullet

- 두 페이지에 중복된 상단 히어로 마크업·CSS를 **공통 컴포넌트 `PageHero`로 추출**하고 페이지 차이는 props와 데스크톱 전용 수정자 클래스로 분리해, 모바일 레이아웃 규칙을 한 파일(`PageHero.css`)에서 관리하도록 정리
- CSS 선택자 우선순위(수정자 0,2,0 vs 공통 0,1,0) 충돌을 막기 위해 **페이지 수정자를 `min-width: 761px` 미디어쿼리 안으로 한정**하는 규칙을 세우고 컴포넌트 JSDoc·CSS 주석에 명시해, 공통 모바일 규칙이 페이지 CSS에 덮이지 않는 구조를 만듦
- `transform: scale()`로 축소한 절대 위치 콜라주를 흐름 안의 고정 높이 상자에 넣고, **단위 없는 CSS 변수 하나로 상자 높이(`* 1px`)와 배율(`/ 350`)을 함께 계산**해 페이지 CSS 세 곳에 흩어져 있던 모바일 수치(200px/.57, 162px/.46, 240px)를 하나의 값으로 통합

> 세 번째 bullet의 "세 곳"은 커밋 `f9fa909` 시점의 `TravelEnjoyPage.css` 760px 규칙(200px, `.57`), 400px 규칙(162px, `.46`), `DestinationsPage.css` 760px 규칙(240px)이다.

## 3. 기술적 의사결정

### 3.1 공통 컴포넌트로 추출할 범위

- **추출한 것**: 골격 마크업(`section > inner > copy + visual`), 모바일 규칙 전체, 데스크톱 기본 치수(여행지 페이지의 기존 값).
- **페이지에 남긴 것**: 문구(`eyebrow`, `title`, `description`, `searchLabel`, `searchHint`), 검색 모달 열기 `onSearch`, 비주얼(`visual` 슬롯), 데스크톱·태블릿 세부 치수(수정자 클래스).
- **슬롯으로 받은 이유**: 여행지는 이미지 한 장, 여행 즐기기는 사진 5장과 아이콘·경로선을 겹친 콜라주다. 비주얼 모양을 컴포넌트가 알 필요가 없으므로 ReactNode 한 칸으로 받고, 대체 텍스트는 페이지가 책임진다(JSDoc).
- **검색 모달은 추출하지 않았다**: 두 페이지가 서로 다른 모달(`TravelSearchModal`, `EnjoySearchModal`)을 쓰므로 `PageHero`는 `onSearch` 콜백만 받는다.
- `title`은 페이지의 유일한 `h1`이다(JSDoc).
- *기록 범위*: 이 추출 범위를 대안과 비교한 문서는 없다. 위 이유는 코드 구조와 JSDoc에서 읽은 것이다.

### 3.2 수정자 규칙은 `@media (min-width: 761px)` 안에만

- **문제**: 페이지 수정자 규칙 `.page-hero--enjoy .page-hero__title`은 클래스 두 개라 우선순위가 (0,2,0)이다. 모바일 공통 규칙 `.page-hero__title`은 (0,1,0)이다. 수정자 규칙이 미디어쿼리 없이 있으면, 760px 이하에서도 공통 모바일 규칙을 이겨 데스크톱 치수가 모바일에 남는다. 파일 순서로도 해결되지 않는다.
- **해결**: 수정자 규칙을 `@media (min-width: 761px)` 또는 `(min-width: 761px) and (max-width: 1100px)` 안에만 둔다.
  - 기존에는 태블릿 규칙이 `@media (max-width: 1100px)`에 있어 760px 이하에도 적용됐다. `f9fa909`에서 히어로 관련 규칙만 `761px ~ 1100px` 범위로 옮기고, 그리드 등 다른 규칙은 그대로 뒀다.
- **규칙을 문서화한 곳**: `PageHero.jsx` JSDoc, `PageHero.css` 머리 주석, 페이지 CSS 주석 세 곳. "페이지별 모바일 조정이 꼭 필요하면 수정자로 공통 규칙을 덮지 말고 CSS 변수만 덮어쓴다"도 함께 적었다.
- **규칙을 스스로 지키도록 고친 부분** (`68e140b`): `f9fa909`에는 여행지 이미지 크기가 `.page-hero--destinations .page-hero__visual img` 수정자 선택자로 걸려 있었고, 760px 규칙 안에 `height: 240px`도 있었다. 이미지 규칙은 모든 폭에 필요하므로 페이지 자체 클래스 `.destination-hero__image`로 바꿔, 수정자가 "데스크톱 전용"이라는 규칙과 어긋나지 않게 했다(커밋 메시지 "Give the destinations image its own class so page modifiers stay desktop-only").
- **대안과 비교 (구조에서 읽은 것, 당시 비교 기록은 없음)**: 공통 모바일 규칙의 우선순위를 올리는 방법(선택자 중복, `!important`)은 다음에 또 덮어쓰기 경쟁을 만든다. 적용 구간 자체를 나누면 두 규칙이 같은 폭에서 만나지 않는다.

### 3.3 `height: 100%` 한 줄로 모바일·데스크톱을 함께 처리 (여행지 이미지)

```css
/* DestinationsPage.css */
.destination-hero__image { display: block; width: 100%; height: 100%; max-height: 540px; object-fit: contain; }
```
- 모바일: `PageHero.css`가 비주얼 상자에 명시적 높이를 주므로 이미지가 상자 높이를 채우고, `object-fit: contain`이라 잘리지 않는다.
- 데스크톱: 상자 높이가 `auto`라 퍼센트 높이가 계산되지 않아 무시되고, 기존처럼 이미지 비율대로 그려진다(`DestinationsPage.css` 주석).
- 그래서 모바일 전용 `height: 240px` 규칙이 필요 없어졌다.

### 3.4 단위 없는 CSS 변수 `--page-hero-visual-h`

```css
/* PageHero.css */
@media (max-width: 760px) {
  .page-hero { --page-hero-visual-h: 200; }
  .page-hero__visual { position: relative; width: 100%; height: calc(var(--page-hero-visual-h) * 1px); margin-top: 32px; }
}
@media (max-width: 400px) {
  .page-hero { --page-hero-visual-h: 160; }
}

/* TravelEnjoyPage.css (760px 이하) */
.enjoy-hero__collage { position: absolute; top: 0; left: 50%; width: 620px; height: 350px;
  transform: translateX(-50%) scale(calc(var(--page-hero-visual-h) / 350)); transform-origin: top center; }
```

- **왜 단위를 뺐나** (`PageHero.css` 주석): 콜라주 배율은 "상자 높이 ÷ 캔버스 원본 높이 350"이다. 변수에 `200px`처럼 단위를 넣으면 `calc(200px / 350px)`처럼 길이를 길이로 나눠야 하는데, 이 연산은 브라우저 지원이 제한적이다. 숫자로 두면 높이는 `* 1px`로 길이로 바꾸고, 배율은 `/ 350`으로 바로 숫자를 얻는다.
- **효과**: 이전(`f9fa909`)에는 높이와 배율을 각 구간에서 따로 적었다(760px 이하 `200px`와 `.57`, 400px 이하 `162px`와 `.46`). 이제 변수 하나만 바꾸면 상자 높이와 배율이 함께 바뀐다. 계산값은 200 ÷ 350 ≈ .571, 160 ÷ 350 ≈ .457로 이전 배율과 거의 같다.
- **두 페이지 높이 통일**: `f9fa909`에서는 여행지 이미지가 240px, 여행 즐기기 상자가 200px로 서로 달랐다. 같은 변수를 쓰면서 두 페이지 모두 200px(400px 이하 160px)이 됐다.
- **페이지별 조정 창구**: 페이지가 모바일 높이를 바꿔야 하면 수정자로 규칙을 덮지 않고 이 변수만 덮어쓴다(3.2 규칙과 연결).

### 3.5 트레이드오프: 여행지 일러스트가 작아짐

- `PageHero.css` 주석과 커밋 `68e140b` 메시지: 여행지 일러스트는 **이전 최대 360×240에서 300×200(401 ~ 760px) / 240×160(400px 이하)** 으로 작아졌다. 여기서 "이전"은 `f9fa909` 시점(모바일 이미지 높이 240px)을 가리킨다. PageHero 작업 전 원래 모바일 이미지 높이는 280px였다(diff).
- **근거** (주석): 400px 이하 공통값 160은 두 비주얼 중 제약이 가장 큰 여행 즐기기 콜라주(회전 포함 폭 약 636px 캔버스)에 맞춘 값이다. 160 ÷ 350 ≈ .457배면 320px에서도 좌우로 잘리지 않는다. 두 페이지 높이를 통일하려고 페이지별로 다르게 두지 않았다.
- **판단**: 여행지 일러스트는 장식 이미지이므로, 검색 버튼이 첫 화면에 더 잘 들어오는 쪽을 택했다(주석).
- **면접에서 정직하게 말할 점**: "검색 버튼이 첫 화면에 더 잘 들어온다"는 판단 근거이고, 기기별로 첫 화면 안에 들어오는지를 측정한 기록은 없다.

### 3.6 접근성 보완

- 콜라주 컨테이너 `div`에 `aria-label`만 있었는데, `aria-label`은 이름을 가질 수 있는 역할에서만 유효하므로 `role="group"`을 함께 붙였다(`f9fa909`, `TravelEnjoyPage.jsx` 주석).
- 검색 버튼에 `:focus-visible` 외곽선을 공통 스타일로 둔다(`PageHero.css`).

## 4. 트러블슈팅 스토리

### 4.1 `transform: scale()`은 레이아웃 크기를 줄이지 않는다 (여행 즐기기 콜라주)

#### Problem
여행 즐기기 콜라주는 사진 좌표가 620×350 캔버스 기준으로 잡혀 있다. 모바일에서는 캔버스째 `scale(.57)`로 줄이는데, 이 콜라주를 PageHero의 흐름 안 비주얼로 옮기면 공간 계산이 맞지 않는다. 또 320 ~ 400px 폭에서는 `.57`배로도 콜라주가 좌우 여백 밖으로 잘린다.

#### Cause
- `transform`은 그리기 단계의 변형이라 레이아웃 박스 크기는 원래 크기(620×350)를 그대로 차지한다. 흐름 안에 그냥 두면 화면에 보이는 높이(약 200px)보다 훨씬 큰 350px 공간을 차지하고, 너비 620px도 좁은 화면에서 넘친다.
- 320 ~ 400px: `.57`배로 줄여도 콜라주 폭이 약 353px(620 × .57)이다. `f9fa909` 주석은 "320~400px 화면에서는 .57배 콜라주(약 353px)가 좌우 여백 밖으로 잘리므로 한 단계 더 축소한다"고 적었다. `68e140b` 주석은 사진 회전을 포함한 캔버스 폭을 약 636px로 보고 400px 이하 값을 정했다.

#### Investigation
- 이전 구현이 콜라주를 절대 위치로 두고 히어로 높이를 770px로 고정했던 이유가 이것이었다. 절대 위치라 레이아웃 크기가 문제가 되지 않는 대신, 높이를 콘텐츠에 맞출 수 없었다.
- 코드 주석(`TravelEnjoyPage.css`)에 원인을 "transform은 레이아웃 크기를 줄이지 않으므로"라고 남겼다.
- *기록 범위*: 문제를 발견한 경위(브라우저에서 본 것인지, 구현 전에 예상한 것인지)와 폭별 측정 결과는 파일에 없다.

#### Solution
1. **흐름 안의 고정 높이 상자**: 비주얼 상자(`.page-hero__visual`)가 축소된 실제 높이만큼의 높이를 갖고 문서 흐름에 들어간다. 콜라주 캔버스는 그 상자 안에 `position: absolute; top: 0; left: 50%`로 두고 `translateX(-50%) scale(…)`, `transform-origin: top center`로 가운데 위에서부터 축소한다. 레이아웃은 상자가, 그리기는 캔버스가 맡는다.
2. **좁은 폭 한 단계 더 축소**: 400px 이하에서 높이와 배율을 한 단계 더 줄였다.
3. **두 값을 하나로 묶음** (`68e140b`): 1·2에서 높이(200/162px)와 배율(.57/.46)을 따로 적던 것을 `--page-hero-visual-h` 하나에서 계산하게 바꿨다(3.4). 높이를 바꾸고 배율 고치는 것을 잊는 실수가 구조적으로 생기지 않는다.

#### Result
- 모바일 히어로는 고정 `min-height`(760/770px) 대신 콘텐츠와 여백으로 높이가 정해진다.
- 콜라주 높이 규칙이 페이지 CSS에서 사라지고 `PageHero.css`의 변수 하나로 모였다.
- 검증 기록: build·lint 통과, 자동 L2 #6에서 `/enjoy`가 h1을 렌더하고 Uncaught 0. **모바일 폭별로 콜라주가 잘리지 않는지 측정한 결과는 파일에 남아 있지 않다.**
- 참고: app-safety-net 자동 L2에서 `/enjoy` 761 ~ 약 800px, 1101 ~ 약 1266px 구간의 콜라주 잘림이 발견됐다. 분석 문서는 이 값이 PageHero 이전 커밋 `98922ee`의 `.enjoy-hero__inner`와 같아 **기존 문제**로 판단했다. 이번 작업은 태블릿·데스크톱 값을 그대로 옮겼기 때문에 이 문제를 고치지도, 새로 만들지도 않았다. 후속 과제로 남아 있다.

#### Learning
- `transform`은 시각 효과이고 레이아웃은 박스 크기로 정해진다. 축소된 요소를 흐름 안에 두려면 "보이는 크기"를 가진 별도 상자가 필요하다.
- 서로 의존하는 두 수치(높이와 배율)를 따로 적으면 언젠가 어긋난다. 한 값에서 파생하게 만드는 것이 유지보수에 유리했다. 이때 CSS 단위 연산의 지원 범위도 설계 제약이 된다.
- 첫 커밋(`f9fa909`)에서 이미 동작은 했지만 수치가 세 곳에 흩어져 있었다. 두 번째 커밋에서 구조를 정리한 것처럼, 동작하는 것과 유지보수 가능한 것을 구분해서 한 번 더 보는 과정이 필요했다.

## 5. 면접 Q&A

### Q1. 두 페이지 히어로를 왜 공통 컴포넌트로 뽑았나요?

**30초 답변**
두 페이지가 같은 골격을 각자 다른 마크업과 CSS로 만들고 있어서 모바일에서 제목 크기, 여백, 비주얼 배치가 1 ~ 2px씩, 또 배치 방식 자체도 달랐습니다. 골격과 모바일 규칙은 `PageHero` 한곳에서 관리하고, 문구와 비주얼은 props로, 데스크톱 세부 치수만 페이지 CSS에 남겼습니다.

**1분 답변**
여행지 페이지는 모바일에서 flex로 세로 정렬하고 이미지를 흐름 안에 뒀는데, 여행 즐기기 페이지는 block 배치에 콜라주를 절대 위치로 두고 히어로 높이를 770px로 고정했습니다. 제목도 47px과 48px처럼 조금씩 달랐습니다. 같은 역할인데 따로 관리하니 한쪽을 고치면 다른 쪽과 어긋나는 구조였습니다. 그래서 공통 골격을 컴포넌트로 만들고, 비주얼은 모양이 완전히 달라서 ReactNode 슬롯으로 받았습니다. 검색 모달도 페이지마다 달라서 `onSearch` 콜백만 받습니다. 데스크톱은 기존 디자인을 유지해야 해서 여행지 값을 기본값으로 쓰고, 여행 즐기기의 데스크톱 치수는 수정자 클래스로 옮겼습니다.

**예상 꼬리 질문**
- *PDCA 문서 없이 진행했는데 범위는 어떻게 정했나요?* → 두 페이지 상단 히어로만 대상으로 했고, 검색 모달이나 본문 섹션은 건드리지 않았습니다. 다만 계획 문서가 없어서 결정 근거가 커밋 메시지와 주석에만 남아 있다는 점은 아쉽습니다.
- *다른 페이지에도 쓸 수 있나요?* → 지금은 두 페이지 전용 골격입니다. 세 번째 페이지가 생기면 그때 props가 충분한지 다시 보겠습니다.

### Q2. CSS 우선순위 충돌은 어떻게 막았나요?

**30초 답변**
페이지 수정자 규칙은 클래스가 두 개라 (0,2,0)이고 모바일 공통 규칙은 (0,1,0)이라, 수정자가 미디어쿼리 없이 있으면 모바일에서도 이깁니다. 그래서 수정자는 `min-width: 761px` 안에만 두는 규칙을 세우고, 컴포넌트 JSDoc과 CSS 주석에 적었습니다.

**1분 답변**
공통 모바일 규칙은 `.page-hero__title`처럼 클래스 하나이고, 페이지별 조정은 `.page-hero--enjoy .page-hero__title`처럼 두 개입니다. 우선순위가 높은 쪽이 파일 순서와 상관없이 이기기 때문에, 데스크톱 치수를 조정하려고 쓴 규칙이 모바일까지 따라옵니다. `!important`나 선택자를 늘려 모바일 규칙을 이기게 할 수도 있지만 그러면 다음에 또 경쟁이 생깁니다. 적용 구간을 나눠서 두 규칙이 같은 폭에서 만나지 않게 했습니다. 기존 태블릿 규칙은 `max-width: 1100px`이라 모바일에도 걸렸는데, 히어로 부분만 761 ~ 1100px로 옮겼습니다. 두 번째 커밋에서는 제가 만든 규칙을 제 코드가 어기고 있던 부분, 즉 여행지 이미지를 수정자 선택자로 걸어 둔 것을 페이지 자체 클래스로 바꿨습니다.

**예상 꼬리 질문**
- *페이지가 모바일에서 꼭 다른 값을 써야 하면요?* → 수정자로 덮지 않고 CSS 변수만 덮어쓰도록 주석에 정해 두었습니다.
- *CSS Modules나 CSS-in-JS를 쓰면 해결되지 않나요?* → 프로젝트가 전역 CSS 파일 구조라 이번 범위에서 방식을 바꾸지 않았습니다. 이 대안을 따로 검토한 기록은 없습니다.

### Q3. CSS 변수에 왜 단위를 넣지 않았나요?

**30초 답변**
같은 값으로 상자 높이와 콜라주 축소 배율을 함께 구하려고요. 배율은 상자 높이 ÷ 350인데, 단위가 있으면 길이를 길이로 나눠야 하고 이 연산은 브라우저 지원이 제한적입니다. 숫자로 두고 높이는 `* 1px`, 배율은 `/ 350`으로 계산했습니다.

**1분 답변**
콜라주는 620×350 캔버스 좌표로 그려져 있어서 모바일에서 캔버스째 축소합니다. 그런데 `transform`은 레이아웃 크기를 줄이지 않으니, 보이는 높이만큼의 상자를 흐름에 두고 그 안에 캔버스를 절대 위치로 넣었습니다. 처음엔 760px 이하에서 200px과 .57, 400px 이하에서 162px과 .46을 따로 적었는데, 높이를 바꾸면 배율도 같이 고쳐야 하는 구조였습니다. 그래서 `--page-hero-visual-h: 200`처럼 숫자 하나만 두고 두 값을 파생시켰습니다. 400px 이하에서는 160으로 바꾸면 배율이 약 .457이 됩니다. 이 변수는 두 페이지가 같이 써서 모바일 비주얼 높이도 자연스럽게 통일됐습니다.

**예상 꼬리 질문**
- *`calc(200px / 350px)`는 정말 안 되나요?* → 코드 주석에는 "길이÷길이 연산은 브라우저 지원이 제한적"이라고만 적었고, 브라우저별 지원 여부를 조사해 기록하지는 않았습니다. 숫자 변수로 두면 지원 여부를 따질 필요가 없어서 그 방식을 택했습니다.
- *여행지 이미지는 이 변수를 어떻게 쓰나요?* → 이미지에 `height: 100%`와 `object-fit: contain`만 주면 모바일에서는 상자 높이를 채웁니다. 데스크톱에서는 상자 높이가 auto라 퍼센트가 무시돼 기존처럼 그려집니다.

### Q4. 통일하면서 잃은 것은 없나요?

**30초 답변**
여행지 일러스트가 모바일에서 최대 360×240에서 300×200, 400px 이하에서는 240×160으로 작아졌습니다. 두 페이지 높이를 맞추려면 제약이 가장 큰 콜라주 기준으로 가야 했고, 일러스트는 장식 이미지라 검색 버튼이 첫 화면에 더 잘 들어오는 쪽을 택했습니다.

**1분 답변**
400px 이하 값 160은 여행 즐기기 콜라주 기준입니다. 콜라주는 회전을 포함하면 폭이 약 636px인 캔버스라, 약 .457배로 줄여야 320px 화면에서도 좌우가 잘리지 않습니다. 페이지마다 높이를 다르게 둘 수도 있었지만, 그러면 통일하려던 목적과 맞지 않습니다. 여행지 일러스트는 정보가 아니라 장식이라 작아져도 기능에는 영향이 없다고 판단했고, 이 트레이드오프를 CSS 주석과 커밋 메시지에 그대로 적어 뒀습니다. 다만 "검색 버튼이 첫 화면에 더 잘 들어온다"는 건 판단 근거이고, 기기별로 측정한 기록은 없습니다.

**예상 꼬리 질문**
- *디자이너나 사용자와 합의했나요?* → 문서에 합의 기록은 없습니다. 주석과 커밋 메시지에 트레이드오프를 남겨 나중에 되돌릴 수 있게 했습니다.

### Q5. 데스크톱에 영향이 없다는 건 어떻게 확인했나요?

**30초 답변**
데스크톱 기본값은 여행지 페이지의 기존 값을 그대로 옮겼고, 여행 즐기기의 데스크톱 값은 761px 이상 수정자 규칙으로 같은 값을 옮겼습니다. 기록으로 남은 확인은 build·lint 통과와, 이후 헤드리스 Chrome 자동 확인에서 두 페이지가 오류 없이 렌더된 것입니다.

**1분 답변**
diff를 보면 여백, 글자 크기, 그리드 열 설정이 같은 값으로 옮겨져 있습니다. 태블릿 규칙도 값은 그대로 두고 적용 구간만 761 ~ 1100px로 좁혔습니다. 이후 app-safety-net 작업의 자동 확인에서 두 페이지를 포함한 14개 라우트가 h1을 렌더하고 Uncaught가 없었습니다. 그때 여행 즐기기의 태블릿 일부 구간에서 콜라주가 잘리는 문제가 발견됐는데, PageHero 이전 커밋과 값이 같아 기존 문제로 분류됐습니다. 솔직히 말하면 데스크톱 화면을 전후로 비교해 측정한 결과는 파일로 남아 있지 않습니다. 다음에는 폭별 스크린샷이나 측정값을 문서로 남기겠습니다.

**예상 꼬리 질문**
- *검색 버튼은 여전히 동작하나요?* → `onSearch` 콜백으로 기존 모달을 여는 구조는 그대로입니다. 다만 자동 확인에서 검색 모달 동작은 따로 측정하지 않았습니다.

## Interview Topics

- React: 공통 컴포넌트 추출 범위, ReactNode 슬롯(`visual`), 콜백 props(`onSearch`)
- CSS: 선택자 우선순위, 미디어쿼리 구간 분리, `transform`과 레이아웃 박스, 절대 위치 + 흐름 안 상자, 단위 없는 CSS 변수와 `calc()`, `height: 100%`가 부모 높이 `auto`에서 무시되는 동작, `object-fit: contain`, `clamp()`
- 반응형: 320 ~ 400px 좁은 폭 대응, 고정 `min-height` 대신 콘텐츠 기반 높이
- 접근성: `aria-label`이 유효하려면 역할(`role="group"`)이 필요함
- 유지보수: 규칙을 JSDoc·CSS 주석에 남겨 다음 작업자가 지키게 하는 것, 트레이드오프를 커밋 메시지에 기록
- 한계 인식: PDCA 없이 진행한 작업의 검증 기록 부족
