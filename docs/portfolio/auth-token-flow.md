## Overview

로그인 응답의 Access Token이 버려지던 상태에서, **토큰 저장 → 요청 전송 → 401 재발급·재시도 → 로그아웃 해제**까지 인증 흐름을 끊김 없이 연결했다. 프론트는 기존 fetch 래퍼(`client.js`)를 확장해 메모리 토큰, Bearer 헤더, single-flight 재발급, 세대 번호 기반 경쟁 조건 차단을 넣었고, `AuthContext`에 세션 복원·로그아웃 결과 반환을 추가했다. 백엔드와는 "401 = 다시 인증하면 해결, 403 = 권한 부족" 계약을 맞췄다.

## Background

- 기존 `LoginPage.jsx`는 `login(response.member)`만 호출해 `accessToken`을 버렸다. 요청 헤더에 토큰이 없고, 재발급·로그아웃 API 호출도 없었다(계획 1.2).
- 백엔드에 `authenticationEntryPoint`가 없어 미인증 요청이 403을 받았고, `/auth/refresh` 실패는 400이었다. 프론트가 "재로그인 필요"와 "권한 없음"을 구분할 수 없었다.
- 이 기능은 이후 피드·댓글·좋아요·북마크·마이페이지 등 로그인 기능 전체의 전제 조건이다(보고서 1.3).

## 1. 포트폴리오 프로젝트 설명용 문단

WayLog는 React와 Spring Boot로 만든 국내 여행 SNS입니다. 로그인 후 토큰이 버려져 보호 API를 전혀 호출할 수 없던 인증 흐름을, 라이브러리 추가 없이 기존 fetch 래퍼와 AuthContext를 확장해 완성했습니다. Access Token은 모듈 메모리에만 두고 새로고침 시 HttpOnly Refresh 쿠키로 세션을 복원하며, 동시에 여러 요청이 401을 받아도 재발급 요청은 하나의 Promise로 공유(single-flight)하고 원 요청은 1회만 재시도합니다. 코드 리뷰에서 지적된 "로그아웃 순간의 토큰 부활" 경쟁 조건은 요청 시점에 인증 세대 번호를 캡처하는 방식으로 막았고, 백엔드와 401/403의 의미를 맞춰 프론트가 상태 코드만으로 분기할 수 있게 했습니다.

## 2. 이력서 bullet

- 기존 fetch 래퍼를 확장해 **메모리 Access Token + HttpOnly Refresh 쿠키 기반 인증 흐름**(Bearer 자동 첨부, 앱 시작 시 세션 복원, 401 시 재발급 후 1회 재시도)을 새 의존성 없이 구현하여, 로그인 응답의 토큰이 버려져 보호 API를 호출할 수 없던 문제를 해결하고 후속 로그인 기능(피드·댓글·북마크)의 기반을 마련
- 동시 401과 React StrictMode 이중 실행에 대비해 **재발급 Promise를 공유하는 single-flight**와 **요청 시점 세대 번호 비교**를 적용하여, 코드 리뷰에서 지적된 로그아웃·재발급 경쟁 조건(로그아웃 화면인데 유효 토큰이 남는 상태)을 수정하고 재리뷰에서 Must Fix 0건으로 머지 판정을 받음
- 백엔드와 **401(재인증 필요)/403(권한 부족) 응답 계약을 `{ message }` JSON으로 정리**하고 "로그인 상태 유지" 해제 시 세션 쿠키로 발급되도록 협업하여, 프론트가 상태 코드만으로 재발급·오류 표시·로그인 해제를 분기하도록 구성 (curl 시나리오 9/10 통과 + 1건 대체 검증)

## 3. 기술적 의사결정

### 3.1 Access Token을 메모리에 보관 (대안: sessionStorage, localStorage)

| 선택지 | 장점 | 단점 |
|--------|------|------|
| **메모리 (선택)** | Web Storage에 토큰이 남지 않아 XSS 스크립트가 저장소에서 토큰을 읽어 가는 경로가 없음 | 새로고침·새 탭이면 사라짐 → 복원 로직 필요 |
| sessionStorage | 새로고침에도 유지, 구현 간단 | 같은 출처 스크립트가 읽을 수 있음 |
| localStorage | 브라우저 종료 후에도 유지 | 같은 출처 스크립트가 읽을 수 있고, 장기 보관 |

- **근거**: 계획 7.2 "XSS 노출 최소화. 사용자 확인". 코드는 `client.js:24`의 모듈 변수 `accessToken` 하나이고, `frontend/src`에서 `localStorage` 사용은 0건이다(분석 1.1 FR-05).
- **메모리 방식의 단점을 메운 방법**
  1. 새로고침 시 토큰 소실 → `AuthProvider` 마운트 시 `authApi.refresh()`로 HttpOnly Refresh 쿠키를 써서 재발급(`AuthContext.jsx:83-108`).
  2. 복원 응답 전 헤더가 "로그인" 버튼으로 깜빡이는 문제 → **토큰이 아닌 표시용 회원 정보만** sessionStorage `waylogMember`에 저장해 먼저 그림(`AuthContext.jsx:17-33`). 실제 로그인 여부는 복원 결과로 확정한다.
  3. 새 탭은 sessionStorage도 비어 있으므로, `isRestoring && !member`일 때 로그인/회원가입 버튼 대신 **같은 클래스의 숨긴 placeholder**를 렌더링해 버튼 깜빡임과 레이아웃 흔들림을 막음(`Header.jsx` R-3, `Header.css`의 `.site-header__placeholder { visibility: hidden }`).
- **면접에서 정직하게 말할 한계**: 메모리 보관은 "저장소에서 토큰을 긁어 가는 경로"를 없애는 것이지, 페이지 안에서 실행되는 XSS 자체를 막는 것은 아니다.

### 3.2 설계안 C(실용 균형) 선택

| 기준 | A. 최소 변경 | B. 클린 아키텍처 | **C. 실용 균형** |
|------|:---:|:---:|:---:|
| 신규 파일 | 0 | 약 5 | 1 |
| 복잡도 | 낮음 | 높음 | 중간 |
| 유지보수성 | 중간 (URL 분산) | 높음 | 높음 |
| 위험 | 낮음 | 중간 | 낮음 |

- **선택 이유** (설계 §2.0): 화면이 인증 URL을 모르게 하면서도 신규 파일을 `src/api/authApi.js` 1개로 제한한다. A는 인증 URL이 화면마다 흩어지고, B(백엔드 핸들러 클래스 분리 등)는 현재 규모에 비해 과하다. 기존 `LoginPage.jsx` 상단 주석이 이미 `authApi.js` 구조를 권장하고 있었다.
- **결과 구조** (설계 §9.2): `화면(LoginPage, Header) → AuthContext → authApi → client`. 화면은 인증 URL을 직접 쓰지 않고(`LoginPage`는 `authApi.login`만 호출), `client.js`는 상위 계층을 import하지 않는다. 구조 일치율 10/10(분석 2.1).

### 3.3 single-flight 재발급

- **문제**: 여러 요청이 동시에 401을 받거나, StrictMode에서 복원 effect가 두 번 실행되면 `/auth/refresh`가 여러 번 나간다(계획 5장 위험 "동시 401로 재발급 요청 여러 번").
- **구현** (`client.js:119-144`): 모듈 변수 `refreshPromise`에 진행 중인 재발급 Promise를 두고, 있으면 그 Promise를 그대로 반환한다. `finally`에서 `refreshPromise === promise`일 때만 비워 다음 재발급을 허용한다.
- **복원과 재시도가 같은 Promise를 공유**: `authApi.refresh()`는 별도 fetch를 만들지 않고 `refreshSession()`에 위임한다(`authApi.js:16-18`). 그래서 앱 시작 복원과 보호 API 401 재시도가 겹쳐도 네트워크 요청은 하나다.
- **StrictMode 처리**: 네트워크 요청은 single-flight로 1회, 상태 적용은 `isActive` 플래그로 첫 번째 effect 실행 결과를 무시해 1회(`AuthContext.jsx:84-107`).
- **무한 루프 방지**: 재시도 조건을 한 줄로 고정했다. `response.status === 401 && !isRetry && !isAuthPath(path)` (`client.js:71`). `/api/v1/auth/**`는 401이 "비밀번호 불일치·재발급 실패"처럼 화면이 처리할 의미이므로 제외하고, 재시도는 `isRetry=true`로 1회만 한다.
- **대안**: axios 인터셉터나 TanStack Query 도입은 계획 7.2에서 "의존성 추가 없이 최소 변경, 라이브러리 도입은 별도 과제"로 제외했다.

### 3.4 세대 번호로 늦게 도착한 응답 무시 (AbortController를 쓰지 않은 이유)

- **구현**: `authGeneration`은 "누가 마지막으로 토큰을 정했는가"를 나타내는 번호로, 로그인·로그아웃(`setAccessToken`)마다 1 증가한다(`client.js:25,29-32`). 재발급 성공 시에는 세대를 올리지 않고 토큰만 저장한다.
  - `request()`: 요청을 **보낸 시점**의 세대를 `sentGeneration`으로 캡처(`client.js:47`).
  - `retryAfterRefresh()`: 재발급 **전**(`:84`)과 **후**(`:99`) 두 번 비교. 바뀌었으면 재발급 결과를 쓰지 않고, 새 세대에 토큰이 있으면 그 토큰으로만 1회 재시도, 없으면 원래 401을 던진다(`retryWithCurrentToken`, `:104-108`).
  - `refreshSession()`: 재발급 시작 시 세대를 기억하고, 끝났을 때 세대가 다르면 받은 토큰으로 덮어쓰지 않는다(`:122,127,133`).
  - `AuthContext`에도 같은 목적의 `authVersionRef`가 있어, 복원 요청 중 로그인·로그아웃이 일어나면 늦게 온 복원 결과를 무시한다(`AuthContext.jsx:44,88,92,96`).
- **AbortController와 비교** — *주의: 계획·설계 문서에 AbortController를 대안으로 비교한 기록은 없다. 아래는 구현된 코드 구조를 근거로 "왜 세대 비교가 이 코드에 맞는지"를 설명하는 내용이며, 면접에서도 "당시 비교표를 만든 것은 아니다"라고 밝히고 말한다.*
  1. **풀어야 할 문제가 "취소"가 아니라 "결과를 적용할지 판단"이다.** 경쟁 조건의 핵심은 로그아웃 이후에 도착한 재발급 결과가 토큰을 되살리는 것이다. 세대 비교는 응답이 언제 도착하든 "이 결과가 현재 인증 상태에 대한 것인가"를 직접 판단한다.
  2. **재발급 Promise는 여러 호출자가 공유한다.** single-flight 구조에서 `/auth/refresh` 하나를 앱 시작 복원과 여러 401 재시도가 함께 기다린다. 한 호출자 사정으로 abort하면 다른 호출자까지 실패한다. 세대 비교는 요청은 그대로 두고 각 호출자가 자기 기준으로 적용 여부만 판단한다.
  3. **변경 범위**: 기존 `request()`는 `signal`을 받지 않는다. abort를 쓰려면 진행 중 요청 목록을 추적하고 모든 호출부에서 `AbortError`를 따로 처리해야 해서, 설계 원칙 "최소 변경"(설계 §1.2)과 맞지 않는다.
  - 반대로 **요청 자체를 끊는 것이 맞는 경우**(복원 요청이 응답 없이 멈추는 경우)에는 `AbortSignal.timeout`을 후속 과제 N-3으로 남겨 두었다. 두 도구의 용도를 구분한 것이다.

### 3.5 401과 403의 의미 분리

- **계약** (설계 §1.1, §6.1):

| 상태 | 의미 | 프론트 처리 |
|------|------|-------------|
| 401 (보호 API) | 토큰 없음·만료·위조 → 다시 인증하면 해결 | 재발급 1회 → 재시도, 재발급 401이면 로그인 상태 해제 |
| 401 (`/api/v1/auth/**`) | 비밀번호 불일치, 인증코드 불일치, 재발급 실패 | 재발급 없이 화면이 폼 오류로 처리 |
| 403 | 로그인했지만 권한 부족 | 재발급해도 결과가 같으므로 그대로 전달 |
| 5xx·네트워크 오류 | 서버·연결 문제, 로그인 여부 판단 불가 | 로그인 상태 유지, 오류 전달 |

- **왜 백엔드까지 맞췄나**: 기존에는 미인증도 403이어서, 프론트가 "403이면 재발급" 규칙을 만들면 권한 부족 요청마다 쓸모없는 재발급이 나가고, "403이면 무시" 규칙을 만들면 만료 토큰을 복구할 수 없었다. 백엔드(`SecurityConfig`)에 401 `authenticationEntryPoint`와 403 `accessDeniedHandler`를 추가하고 기존 `GlobalExceptionHandler`와 같은 `{ "message": ... }` 형식으로 맞췄다.
- **재발급 실패의 401/500 경계** (리뷰 R-5): 처음에는 `/auth/refresh`가 `catch (Exception)`으로 모든 예외를 401 + 쿠키 삭제로 처리해, DB 오류 같은 서버 결함도 사용자를 로그아웃시킬 수 있었다. 토큰·회원 검증 실패만 401 + 쿠키 삭제, 그 밖은 500 + 쿠키 유지로 좁혔다. 프론트는 이미 "401일 때만 상태 해제"(`client.js:90`, `AuthContext.jsx:99`) 규칙이라 코드 변경 없이 맞물렸다.
- **curl 확인** (분석 5.1): 토큰 없는 보호 API 401 `{"message":"로그인이 필요합니다."}`, 일반 회원 `/admin/notices` 403 `{"message":"접근 권한이 없습니다."}`, 잘못된 쿠키 refresh 401, 정상 refresh 200 + `member`.

### 3.6 콜백 주입으로 순환 의존 회피

- **문제**: 보호 API 재발급이 실패하면 `client.js`가 `AuthContext`의 `member`를 비워야 한다. 그러나 `AuthContext`는 이미 `client.js`를 import하므로, 반대로 import하면 순환 의존이 된다.
- **구현**: `client.js`는 `setSessionExpiredHandler(handler)`만 export하고(`client.js:35-37`), `AuthContext`가 마운트 시 콜백을 등록하고 언마운트 시 `null`로 해제한다(`AuthContext.jsx:74-80`). 재발급 401이고 세대가 그대로일 때만 `sessionExpiredHandler?.()`를 호출한다(`client.js:94`).
- **효과**: `client.js`는 React를 전혀 모르는 HTTP 인프라 계층으로 남는다(설계 §2.3 "client 의존 대상: 없음(fetch)"). 코드 리뷰 Keep 항목에도 "`authApi.js`와 콜백 주입으로 순환 의존 회피"가 들어갔다(분석 6장).
- **대안**: 이벤트 버스나 전역 상태 라이브러리도 가능하지만, 알릴 대상이 하나(세션 만료)뿐이라 함수 하나 등록으로 충분했다. 대안 비교 기록은 문서에 없으므로 면접에서는 "구조상 이 정도면 충분하다고 판단했다" 수준으로 말한다.

## 4. 트러블슈팅 스토리

### 4.1 (a) "로그인 상태 유지" 체크박스가 세션 복원과 결합해 무의미해진 문제 (R-1)

#### Problem
"로그인 상태 유지"를 **해제**하고 로그인해도, 브라우저를 다시 열면 자동으로 로그인됐다. 공용 PC에서 다음 사용자가 이전 사용자 계정으로 들어갈 수 있는 보안 문제였고, 코드 리뷰에서 **Must Fix**로 분류돼 머지 판정이 "조건부 머지"가 됐다.

#### Cause
두 결정이 따로는 문제가 없었지만 결합하면서 생긴 문제다.
1. 계획 단계에서 체크박스 동작은 범위 밖으로 뺐다(계획 7.2). 프론트는 `rememberLogin`을 이미 보내고 있었지만 백엔드 사용처는 0건이었고, `JwtConfig`는 항상 7일(`Max-Age`) Refresh 쿠키를 발급했다.
2. 같은 계획에서 "앱 시작 시 자동 복원"을 넣었다. 7일 쿠키가 남아 있으면 브라우저 재실행 때 `AuthProvider`가 `/auth/refresh`로 세션을 복원한다.

복원 기능이 생기기 전에는 체크박스가 동작하지 않아도 눈에 띄지 않았지만, 복원이 생기자 "체크 해제"가 사용자에게 아무 의미가 없게 됐다.

#### Investigation
- 브라우저에서 발견한 것이 아니라 **Check 단계 코드 리뷰(frontend-code-reviewer)** 에서 찾았다. 리뷰는 값의 흐름을 끝까지 따라갔다: `LoginPage.jsx`에서 `rememberLogin`을 보냄 → 백엔드에서 사용처 0건 → `JwtConfig`가 항상 7일 쿠키 → `AuthContext.jsx`의 마운트 시 복원.
- 계획 문서의 제외 항목(체크박스)과 포함 항목(자동 복원)을 **함께** 놓고 봐야 드러나는 문제였다.

#### Solution
사용자 결정으로 범위를 바꿔 FR-12로 포함했다(백엔드 담당 에이전트 구현, 프론트는 협업 관점).
- `UserRequest`에 `Boolean rememberLogin` 추가. **래퍼 타입**을 써서 값을 보내지 않는 기존 클라이언트는 `null` → 기존 동작(7일)으로 하위 호환.
- `AuthService.login`: `!Boolean.FALSE.equals(request.getRememberLogin())` — `false`일 때만 세션 쿠키.
- `JwtConfig.createRefreshTokenCookie(token, persistent)`: `persistent`가 false면 `Max-Age`를 넣지 않아 브라우저 종료 시 삭제되는 세션 쿠키로 발급. 토큰 자체 만료는 그대로.
- `/auth/refresh`는 Refresh 쿠키를 다시 발급하지 않으므로 처음 정한 쿠키 유형이 유지된다.
- **프론트 변경 없음**: `authApi.login({ email, password, rememberLogin })`이 이미 값을 보내고 있었다. 화면·API 계층을 분리해 둔 덕에 계약만 맞추면 됐다.

#### Result
- 백엔드 curl: `rememberLogin` false/true/생략/null 각각의 쿠키 유형 확인, 세션 쿠키로 받은 토큰의 refresh 200 통과(분석 9장).
- Vite 프록시 경유 로그인(`rememberLogin=false`)에서 `Set-Cookie: refreshToken=...; Path=/; Secure; HttpOnly; SameSite=Strict`, `Max-Age` 없음 확인(보고서 6.2).
- 재리뷰에서 R-1 해결, Must Fix 0 → "머지 가능".
- **검증 한계**: 브라우저 완전 종료 후 재실행 시나리오(L2-13·14)는 사용자 수동 확인에서 큰 오류는 없었으나 항목별 결과는 기록하지 않았다.
- **남은 한계**(N-4): 브라우저의 "이전 세션 계속" 설정은 세션 쿠키를 복원할 수 있고, 토큰 자체는 7일 유효하다.

#### Learning
- 범위에서 **뺀 항목**이 **넣은 항목**과 결합했을 때 사용자에게 보이는 동작이 어떻게 바뀌는지를 계획 단계에서 교차 점검해야 한다(보고서 7.3 Try).
- UI에 컨트롤이 있으면 사용자는 동작한다고 믿는다. 동작하지 않는 체크박스는 "기능 없음"보다 나쁠 수 있다.
- 세션 쿠키는 근본 대책이 아니다. 비유지 로그인이면 토큰 만료 자체를 짧게 하는 방식이 더 확실하다(후속).

### 4.2 (b) 로그아웃 순간 진행 중이던 요청 때문에 토큰이 되살아나는 경쟁 조건 (R-2)

#### Problem
로그아웃하는 순간 이미 나가 있던 보호 API 요청이 401을 받으면, 재발급이 성공해 **"화면은 로그아웃 상태인데 메모리에는 유효한 토큰이 남는"** 상태가 될 수 있었다. 사용자는 로그아웃했다고 믿지만 이후 요청에는 다시 Bearer 토큰이 붙는다.

#### Cause
세대 번호를 **401을 받은 시점**에 읽은 것이 원인이다.

```
1. 요청 A 전송 (세대 1, 토큰 T)
2. 사용자 로그아웃 → setAccessToken(null), 세대 1 → 2, /auth/logout 호출 (쿠키 삭제는 아직 응답 전)
3. 요청 A가 401 수신
4. (수정 전) 이 시점의 세대 2를 기준으로 refreshSession 시작
5. Refresh 쿠키가 아직 삭제 전이면 재발급 200
6. 재발급 시작 세대(2) == 현재 세대(2) → "변경 없음"으로 판단해 새 토큰 저장
→ 로그아웃 화면 + 유효 토큰
```

재발급 도중의 세대 변경은 이미 막고 있었지만, 기준 세대를 401 시점에 잡으니 **요청을 보낸 뒤 ~ 401 수신 전** 사이의 로그아웃을 놓쳤다.

#### Investigation
- 1차 코드 리뷰(R-2)가 `client.js`의 401 처리와 `refreshSession`의 세대 비교 코드를 따라가며 위 순서를 재구성해 원인을 짚었다. gap 분석도 같은 문제를 M-6(확신도 55%)으로 따로 올렸다.
- 이벤트 순서를 시간축에 놓고 "각 단계에서 세대 번호를 **언제** 읽는가"를 확인한 것이 핵심이었다. 비교 로직은 맞았지만 **기준값을 캡처하는 시점**이 틀렸다.
- 실제 브라우저에서 재현한 버그가 아니라 코드 경로 분석으로 찾은 잠재 버그다. 당시 보호 API를 호출하는 화면이 없어 사용자에게 드러나지는 않았다.

#### Solution
세대를 **요청을 보낸 시점**에 캡처하고, 재발급 전후로 두 번 비교했다(설계 §12 R-2).

```js
// client.js:47 — request() 시작 시
const sentGeneration = authGeneration

// client.js:84 — 재발급 전: 요청 후 로그인·로그아웃이 있었다면 재발급하지 않음
if (sentGeneration !== authGeneration) return retryWithCurrentToken(path, options, originalError)

// client.js:99 — 재발급 후: 재발급 도중 세대가 바뀌었어도 같은 규칙
if (sentGeneration !== authGeneration) return retryWithCurrentToken(path, options, originalError)
```

- `retryWithCurrentToken`: 새 세대에 토큰이 있으면(그 사이 다시 로그인) 그 토큰으로 1회 재시도, 없으면(로그아웃) 원래 401을 그대로 던진다.
- 재발급 실패(401) 시 만료 콜백도 `sentGeneration === authGeneration`일 때만 호출해, 이미 지난 상태에 대한 실패가 새 로그인 상태를 지우지 않게 했다(`client.js:94`).
- 정상 흐름을 깨지 않도록 `refreshSession`은 세대를 올리지 않고 토큰만 저장한다. 그래서 401 → 재발급 → 재시도, single-flight, 무한 루프 방지가 그대로 유지된다.

#### Result
- 재리뷰(분석 9.7)가 지난 리뷰의 문제 순서를 다시 따라가 확인했다: 로그아웃 **전에 보낸** 요청은 `/auth/refresh`를 아예 보내지 않고, 재발급 도중 로그아웃해도 토큰을 저장하지 않는다. R-2 해결, 머지 가능.
- 콘솔 재현 시나리오(L2-19: 잘못된 토큰으로 요청 → 즉시 `setAccessToken(null)` → 401, `/auth/refresh` 호출 없음 기대)를 계획했으나, 브라우저 결과는 항목별로 기록하지 않았다.
- **남은 범위**: 로그아웃 **후**, `/auth/logout` 응답 **전**에 새로 보낸 보호 API 요청은 막지 못한다. 현재 보호 API 화면이 없어 실제 영향은 없는 것으로 판단했다(분석 9.6, 확신도 80% 미만).

#### Learning
- 비동기 경쟁 조건은 "비교를 하느냐"보다 **"기준값을 언제 캡처하느냐"** 가 더 중요하다. 요청의 소유권은 요청을 보낸 순간에 정해진다.
- 이벤트를 시간축에 늘어놓고 각 시점의 공유 상태 값을 적어 보는 방식이, 재현하기 어려운 경쟁 조건을 찾는 데 효과적이었다.
- 세대 카운터가 `client.js`(`authGeneration`)와 `AuthContext`(`authVersionRef`) 두 곳에 생겼다. 다음에는 처음부터 하나로 설계하겠다(후속 R-10).
- 경쟁 조건은 수동 테스트로 재현하기 어렵다. 콘솔 시나리오를 자동 테스트로 남겨야 회귀를 막을 수 있다.

## 5. 면접 Q&A

### Q1. 새로고침하면 메모리 토큰이 사라지는데, 어떻게 로그인을 유지했나요?

**30초 답변**
Access Token은 XSS로 저장소에서 읽히지 않게 모듈 변수에만 두고, 새로고침되면 앱 시작 시 HttpOnly Refresh 쿠키로 `/auth/refresh`를 호출해 토큰과 회원 정보를 다시 받습니다. 복원 응답이 오기 전 헤더가 깜빡이지 않도록 토큰이 아닌 닉네임 같은 표시 정보만 sessionStorage에 두었습니다.

**1분 답변**
WayLog는 Access Token을 `client.js`의 모듈 변수에만 보관합니다. 그래서 새로고침하면 토큰이 사라지는데, `AuthProvider`가 마운트될 때 `authApi.refresh()`를 호출해서 HttpOnly Refresh 쿠키로 새 토큰을 받습니다. 이때 백엔드와 협의해 refresh 응답에 login과 같은 형태의 `member`도 받도록 해서 헤더 닉네임까지 한 번에 복원합니다. 결과는 세 갈래로 나눴습니다. 200이면 회원 갱신, 401이면 세션이 없으니 비로그인, 네트워크나 500 오류면 판단할 수 없으니 기존 표시를 유지합니다. UX 쪽으로는 복원 전 "로그인" 버튼이 먼저 보이는 문제가 있어서, 표시용 회원 정보만 sessionStorage에 두고, 그마저 없는 새 탭에서는 버튼 대신 같은 크기의 숨긴 placeholder를 그렸습니다.

**예상 꼬리 질문**
- *sessionStorage에 회원 정보를 두는 건 괜찮나요?* → 토큰이 아니라 닉네임 같은 표시 정보뿐이고, 실제 로그인 여부는 복원 결과로 확정합니다. 복원이 401이면 바로 지웁니다.
- *메모리에 두면 XSS에서 안전한가요?* → 저장소에서 토큰을 읽어 가는 경로는 없어지지만, 페이지 안에서 실행되는 XSS 자체를 막는 것은 아닙니다. 그 한계는 인지하고 있습니다.
- *StrictMode에서 복원 effect가 두 번 실행되면요?* → 재발급 Promise를 공유해서 네트워크 요청은 1회이고, 첫 실행 결과는 `isActive` 플래그로 무시해 상태 적용도 1회입니다.
- *복원 요청이 응답 없이 멈추면요?* → 현재는 timeout이 없어 placeholder가 계속 보일 수 있습니다. `AbortSignal.timeout`을 후속 과제로 남겼습니다.

### Q2. 401이 동시에 5개 오면 재발급은 몇 번 나가나요?

**30초 답변**
1번입니다. 진행 중인 재발급 Promise를 모듈 변수에 두고, 두 번째 요청부터는 새 요청을 만들지 않고 그 Promise를 기다리게 했습니다(single-flight). 재발급이 끝나면 5개 요청이 각각 새 토큰으로 1번씩만 재시도합니다.

**1분 답변**
`refreshSession()`은 `refreshPromise`가 있으면 그대로 반환하고, 없을 때만 `/auth/refresh`를 보냅니다. `finally`에서 자기 Promise일 때만 비워서 다음 재발급을 허용합니다. 5개 요청은 모두 같은 Promise를 기다렸다가, 성공하면 각자 `isRetry=true`로 한 번만 재시도합니다. 재시도에서 또 401이면 다시 재발급하지 않고 오류를 던지므로 무한 루프가 없습니다. 재발급이 401로 실패하면 토큰을 비우고 세션 만료 콜백으로 헤더를 비로그인으로 바꾸고, 각 요청은 원래 401을 던집니다. 또 앱 시작 복원도 같은 `refreshSession`을 쓰기 때문에, 복원과 보호 API 401이 겹쳐도 요청은 하나입니다.

**예상 꼬리 질문**
- *실제로 1번인지 확인했나요?* → 코드 리뷰와 정적 분석으로 확인했고, 콘솔에서 잘못된 토큰으로 두 요청을 동시에 보내는 시나리오(L2-7)를 준비했습니다. 브라우저 수동 확인에서는 큰 오류가 없었지만 시나리오별 결과는 기록하지 못했습니다. 다음에는 자동 테스트로 남기겠습니다.
- *재발급이 실패하면 만료 콜백이 5번 불리지 않나요?* → 세대가 그대로인 요청마다 호출될 수 있지만, 콜백은 회원 정보를 `null`로 두는 동작이라 여러 번 불려도 결과가 같습니다.
- *왜 axios 인터셉터를 쓰지 않았나요?* → 기존 fetch 래퍼가 이미 있었고, 이번 범위에서는 새 의존성을 추가하지 않기로 했습니다. 라이브러리 도입은 별도 과제로 뒀습니다.
- *`/auth/login`이 401이면요?* → `/api/v1/auth/**`는 재발급 대상에서 제외해 "비밀번호 불일치"가 그대로 폼 오류로 표시됩니다.

### Q3. 가장 까다로웠던 버그는 무엇이고, 어떻게 원인을 찾았나요? (R-2)

**30초 답변**
로그아웃하는 순간 진행 중이던 요청이 401을 받으면 재발급이 성공해, 로그아웃 화면인데 유효한 토큰이 남는 경쟁 조건이었습니다. 원인은 세대 번호를 401을 받은 시점에 읽은 것이었고, 요청을 보낸 시점에 캡처하도록 바꿨습니다.

**1분 답변**
로그인·로그아웃마다 증가하는 `authGeneration`으로 늦게 도착한 재발급 결과를 무시하고 있었는데, 코드 리뷰에서 빈틈이 지적됐습니다. 요청을 보낸 뒤 로그아웃하면 세대가 올라가는데, 그 후에 401을 받으면 이미 올라간 세대를 기준으로 재발급을 시작합니다. 로그아웃 API가 쿠키를 지우기 전이면 재발급이 성공하고, 재발급 중에는 세대가 바뀌지 않았으니 토큰을 저장해 버립니다. 이벤트를 시간축에 늘어놓고 각 시점에 세대를 언제 읽는지 따라가서 원인을 확인했습니다. 해결은 `request()` 시작 시 `sentGeneration`을 캡처하고, 재발급 전과 후 두 번 비교하는 것입니다. 바뀌었으면 재발급 결과를 쓰지 않고, 새 세대에 토큰이 있을 때만 그 토큰으로 재시도합니다. 재리뷰에서 같은 순서를 다시 따라가 해결을 확인했습니다.

**예상 꼬리 질문**
- *브라우저에서 재현했나요?* → 코드 경로 분석으로 찾은 잠재 버그입니다. 당시 보호 API 화면이 없어 사용자에게 드러나지 않았고, 콘솔 재현 시나리오는 준비했지만 결과를 항목별로 기록하지 못했습니다.
- *아직 남은 경우는요?* → 로그아웃 후, 로그아웃 응답 전에 새로 보낸 요청은 막지 못합니다. 현재 영향은 없다고 판단했지만 보호 API 화면이 생기면 다시 봐야 합니다.
- *왜 AbortController로 취소하지 않았나요?* → 문제는 요청 취소가 아니라 늦은 결과를 적용할지 판단하는 것이었고, 재발급 Promise를 여러 호출자가 공유하기 때문에 한 곳에서 abort하면 다른 호출자까지 실패합니다. 당시 비교표를 만든 것은 아니고, 코드 구조상 세대 비교가 맞다고 판단한 것입니다.

### Q4. 왜 백엔드의 401/403까지 손댔나요? 프론트에서 처리하면 안 되나요?

**30초 답변**
기존에는 미인증도 403이어서 프론트가 "재발급하면 해결되는 상황"과 "권한이 없는 상황"을 구분할 수 없었습니다. 백엔드와 401은 재인증, 403은 권한 부족으로 계약을 맞춰, 프론트는 401일 때만 재발급하도록 했습니다.

**1분 답변**
403에 재발급을 붙이면 일반 회원이 관리자 API를 호출할 때마다 쓸모없는 재발급이 나가고, 403을 무시하면 만료 토큰을 복구할 수 없습니다. 그래서 Spring Security에 401 entryPoint와 403 accessDeniedHandler를 추가하고, 기존 오류 형식과 같은 `{ message }` JSON으로 맞췄습니다. 프론트 기준으로 규칙을 표로 정리했습니다. 보호 API 401은 재발급 후 재시도, 인증 API 401은 화면이 처리, 403은 그대로 전달, 5xx와 네트워크 오류는 로그인 상태 유지입니다. 리뷰에서 refresh가 모든 예외를 401로 바꿔 DB 오류에도 로그아웃될 수 있다는 지적이 나와서, 토큰·회원 검증 실패만 401로 좁히고 나머지는 500으로 바꿨습니다. 프론트는 이미 "401일 때만 해제" 규칙이라 코드 변경 없이 맞물렸습니다.

**예상 꼬리 질문**
- *공개 API에 만료된 토큰을 보내면 401이 나오지 않나요?* → 기존 JWT 필터가 잘못된 토큰이면 인증 정보를 비우고 통과시키므로 permitAll API는 그대로 200입니다. curl로 회귀를 확인했습니다.
- *백엔드는 직접 구현했나요?* → 백엔드 담당 에이전트가 구현했고, 저는 프론트가 필요한 계약(상태 코드 의미, 응답 형식, refresh 응답의 member)을 정의하고 검증하는 쪽이었습니다.
- *500 응답 body 형식은요?* → 형식을 보장하지 않기 때문에 프론트는 status 코드만 보고 처리하도록 했습니다.

### Q5. 컴포넌트와 모듈은 왜 이렇게 나눴나요?

**30초 답변**
`화면 → AuthContext → authApi → client` 한 방향으로 의존하게 했습니다. 화면은 인증 URL을 모르고, HTTP 계층인 `client.js`는 React를 모르게 해서, 세션 만료는 콜백 등록으로만 알립니다.

**1분 답변**
설계안을 세 가지 비교했습니다. 신규 파일 없이 화면에서 바로 호출하는 A는 인증 URL이 흩어지고, 파일을 5개쯤 새로 만드는 B는 현재 규모에 과했습니다. 그래서 `authApi.js` 하나만 추가하는 C를 골랐습니다. `LoginPage`는 `authApi.login`만 부르고, `AuthContext`가 토큰과 회원 상태를 함께 바꿉니다. 순환 의존 문제도 있었습니다. 재발급이 실패하면 `client.js`가 회원 상태를 비워야 하는데, `AuthContext`가 이미 `client.js`를 import하기 때문입니다. 그래서 `client.js`는 `setSessionExpiredHandler`만 내보내고 `AuthContext`가 마운트 시 콜백을 등록하게 했습니다. 이 구조 덕분에 "로그인 상태 유지" 이슈를 백엔드에서 고칠 때 프론트 코드는 바꿀 필요가 없었습니다.

**예상 꼬리 질문**
- *서비스가 커지면 뭘 바꾸겠나요?* → 세대 카운터를 하나로 합치고, 보호 API 화면이 늘면 서버 상태 라이브러리 도입을 별도로 검토하겠습니다. 지금도 회원가입 화면이 인증 URL을 직접 쓰고 있어 `authApi`로 통합할 계획입니다.
- *Context 값이 바뀌면 전체가 리렌더링되지 않나요?* → `login`, `logout`은 `useCallback`, value는 `useMemo`로 고정해 `member`, `isRestoring`이 바뀔 때만 새 객체가 됩니다. 리렌더링 횟수를 측정하지는 않았습니다.

### Q6. 로그아웃 UX는 어떻게 처리했나요? 서버 호출이 실패하면요?

**30초 답변**
화면은 즉시 비로그인으로 바꾸고 나서 로그아웃 API를 호출합니다. `logout()`이 성공 여부를 boolean으로 반환하게 해서, 실패하면 헤더에 "로그아웃이 완료되지 않았을 수 있습니다" 알림과 "다시 시도" 버튼을 보여줍니다.

**1분 답변**
처음 구현에서는 로그아웃 API 실패를 조용히 무시했는데, 리뷰에서 지적을 받았습니다. 쿠키 삭제가 실패하면 새로고침할 때 세션 복원으로 다시 로그인되는데, 사용자는 그걸 알 수 없습니다. 그래서 `AuthContext.logout()`은 토큰과 회원 상태를 먼저 비워 즉시 반응하고, 서버 호출 결과를 true/false로 반환하게 바꿨습니다. `Header`는 실패하면 `role="alert"` 알림 카드를 띄웁니다. 알림 시점에는 이미 로그아웃 버튼이 사라졌기 때문에, 복구 수단으로 "다시 시도"와 "닫기" 버튼을 넣었고, 재시도 중에는 "처리 중..."으로 버튼을 비활성화합니다.

**예상 꼬리 질문**
- *왜 서버 응답을 기다리지 않고 먼저 비우나요?* → 사용자 입장에서 로그아웃은 즉시 반영돼야 하고, 토큰을 먼저 지워야 이후 요청에 토큰이 붙지 않습니다. 세대 번호도 이때 올라가 진행 중인 재발급 결과를 무시하게 됩니다.
- *알림 카드가 모바일에서는요?* → 너비를 `min(300px, calc(100vw - 32px))`로 잡아 좁은 화면에서도 화면 밖으로 나가지 않게 했습니다.

### Q7. 이번 작업에서 다시 한다면 무엇을 다르게 하겠나요?

**30초 답변**
세 가지입니다. 범위에서 뺀 항목이 넣은 항목과 결합할 때의 동작을 계획 단계에서 점검하고, 세대 카운터를 처음부터 하나로 설계하고, 브라우저 검증을 시나리오 번호별로 기록하거나 자동화하겠습니다.

**1분 답변**
"로그인 상태 유지"를 범위 밖으로 뺐는데, 같은 계획의 자동 복원과 결합하니 체크 해제가 무의미해졌고 이걸 Check 단계 리뷰에서야 알았습니다. 계획 단계에서 제외 항목을 교차 점검했으면 더 일찍 잡았을 겁니다. 또 늦은 응답을 막는 세대 카운터가 `client.js`와 `AuthContext`에 하나씩 생겼는데, 목적이 같으니 처음부터 하나로 두는 게 맞았습니다. 마지막으로 브라우저 확인을 사용자에게 받았지만 시나리오별 결과를 남기지 않아, 경쟁 조건 같은 항목의 통과 여부를 근거로 제시할 수 없습니다. 다음에는 체크리스트로 받고, 반복 시나리오는 Playwright 같은 자동화를 검토하겠습니다.

**예상 꼬리 질문**
- *왜 지금 바로 자동화하지 않았나요?* → 새 의존성이 필요한 작업이라 사용자 확인이 필요한 별도 과제로 뒀습니다.

## 7. 알려진 한계와 개선 계획

보고서 4.1 이월 항목 가운데 면접에서 나올 만한 것만 골랐다. "알고 있고, 이렇게 개선할 계획"의 형태로 말한다.

| 항목 | 알고 있는 한계 | 개선 계획 |
|------|----------------|-----------|
| **R-10 / N-1 세대 카운터 이중화** | 같은 목적의 카운터가 `client.js`의 `authGeneration`과 `AuthContext`의 `authVersionRef` 두 곳에 있다. 재발급 대기 중 세대가 바뀌고 재발급이 401로 끝나면 새 토큰이 있어도 원래 401을 던지는 등 성공 경로와 동작 차이가 있다. | 세대를 `client.js` 한 곳에서 관리하고 Context는 그 값을 참조하도록 통일하면서 N-1 분기도 함께 정리한다. |
| **R-9 재시도 경로의 member 미갱신** | 보호 API 401 → 재발급 성공 시 토큰만 갱신하고 헤더 회원 정보는 갱신하지 않는다. 토큰이 유효하면 로그인 상태는 유지되므로 우선순위는 낮게 두었다. | 재발급 성공도 콜백으로 알려 `AuthContext`가 `member`를 동기화하도록 한다. |
| **N-4 세션 쿠키의 한계** | "로그인 상태 유지" 해제 시 세션 쿠키를 쓰지만, 브라우저의 "이전 세션 계속" 설정은 세션 쿠키를 복원할 수 있고 토큰 자체는 7일 유효하다. | 근본 대책으로 비유지 로그인일 때 Refresh Token 만료 자체를 짧게 발급하도록 백엔드와 협의한다. |
| **N-3 복원 timeout 없음** | 백엔드가 응답 없이 멈추면 복원 placeholder가 계속 보인다. | `AbortSignal.timeout`으로 복원 요청에 제한 시간을 두고, 네트워크 오류 한국어 문구(R-7)와 함께 처리한다. |
| **R-11 / M-3 쿠키 없는 refresh의 삭제 Set-Cookie** | 쿠키 없이 나간 복원 요청이 늦게 401로 돌아오면서, 그 사이 로그인으로 받은 새 Refresh 쿠키를 삭제할 가능성이 있다(확신도 80% 미만). 클라이언트 상태는 세대 비교로 보호되지만 쿠키는 서버 응답이 직접 지운다. | 쿠키가 없을 때는 삭제 `Set-Cookie`를 보내지 않도록 백엔드와 조정한다. |
| **R-6 grade null 회원** | 응답은 role을 `"user"`로 채우지만 JWT 필터는 grade null에서 예외가 나 익명 처리되어, 해당 회원은 로그인은 되지만 보호 API가 계속 401이다. 프론트는 재시도 1회 제한 덕분에 무한 루프는 없다. | 필터에도 같은 기본값을 적용하도록 백엔드와 맞춘다. 프론트 관점의 교훈은 "응답 계약과 필터 동작이 같은 기본값을 써야 한다"는 것. |
| **M-8 회원가입 화면의 인증 URL 직접 사용** | `SignupPage`는 이번 범위 밖이라 여전히 인증 URL을 직접 호출한다. | `authApi`로 통합해 "화면은 인증 URL을 모른다" 규칙을 전체에 적용한다. |
| **Refresh Token 회전·서버 측 폐기** (계획 2.2 제외) | 탈취된 Refresh Token을 서버에서 무효화할 수 없다. | 후속 기능으로 회전과 폐기 목록을 백엔드와 함께 설계한다. |
| **L2 검증 기록 누락** | 브라우저 확인은 "큰 오류 없음"만 남고 시나리오별 결과가 없다. 특히 경쟁 조건(L2-19), 브라우저 재시작(L2-13·14), 로그아웃 실패(L2-17·18)는 근거가 약하다. | 시나리오 번호별 체크리스트로 기록하고, 반복 시나리오는 Playwright 자동화를 검토한다(새 의존성이므로 사용자 확인 필요). |
